# OMP profiles, identity, and discovery

A rotom profile selects public resources and private machine overrides. An OMP native profile holds the resulting configuration, authentication, sessions, and caches. These are separate identities.

| Property | rotom profile | OMP native profile |
| --- | --- | --- |
| Name | Registered ID such as `omp-kernel` | `rotom-` plus the first 24 hexadecimal characters of the profile ID's SHA-256 |
| Selection | `agentcfg --profile ID` | Leading `--profile NAME` generated by the managed launcher |
| Ownership | Machine, local configuration, state, and physical instance | Storage within that instance's state home |
| Switching | Selects a separate instance | Authentication and sessions stay with that instance |

Readable directory names may be shortened, but ownership checks include the complete ID, complete hash, and physical path. Renaming a profile creates a new identity. Editing a native name does not transfer ownership or authentication. Existing native default and named profiles are not adopted automatically.

## Storage and execution environment

```text
<instance>/
  .agentcfg-omp-owner.json
  .agentcfg-omp.lock
  user-home/
    .omp/profiles/<native-name>/agent/
    .config/
    .local/share/
    .local/state/
    .cache/
```

New deployments preserve the launcher's HOME and XDG directories for tools. A generated relative `PI_CONFIG_DIR` and the native `--profile` keep OMP configuration, authentication, and sessions in the existing managed `user-home/.omp`. The physical identity and owner remain unchanged; native data is not moved. Older deployments retain their saved isolated-HOME contract until an explicit `plan` and `apply` update it.

Some native features also read outside the named profile. Default keybindings can still be inherited from the managed configuration root's `.omp/agent/keybindings.yml`. Discovery reports include that path and its digest; the manager does not delete the file to suppress inheritance. Diagnostic `home` and `state_home` fields describe storage. `planned_execution_environment` describes a proposed environment, not proof that an old deployment has changed.

The environment allowlist includes basic terminal variables, Git configuration paths, `ZDOTDIR`, dynamic-library paths, and Python/Node/virtual-environment paths. Declare additional variables in machine `environment.inherit` or `environment.values`. The entire shell environment is not inherited. Noninteractive tools do not automatically receive interactive shell functions. The ordinary native Bash tool uses OMP's embedded execution backend and does not promise full zsh language semantics.

OMP may select existing `<XDG_CATEGORY>/omp` or `profiles/<name>` directories for some authentication, cache, and lease paths. The manager checks effective upstream paths and rejects layouts that redirect existing storage. It does not create redirect directories or migrate data automatically. Such a conflict returns 4. Changes to HOME/XDG also require review through `plan` and `apply`.

Native profile precedence is explicit `--profile`, then `OMP_PROFILE`/`PI_PROFILE`. A named profile is not a `PI_CODING_AGENT_DIR` relocation. Native default storage is `.omp/agent`, not `.omp/profiles/default/agent`.

Do not declare `OMP_PROFILE`, `PI_PROFILE`, `PI_CODING_AGENT_DIR`, `PI_CONFIG_DIR`, session-directory overrides, or broker/gateway control variables in the calling environment or machine environment. The launcher generates identity variables and rejects conflicting overrides. Other hosts' authentication directories are not passed to OMP.

## Discovery policy

Undeclared project and external configuration is disabled. Checks cover cwd and all its ancestors. Compatibility providers for `.agents`, `.agent`, `.claude`, `.codex`, `.gemini`, and top-level `AGENTS.md`, `CLAUDE.md`, and `GEMINI.md` are disabled: these paths may exist without their contents being loaded or causing a conflict.

Native `.omp` resources, dotenv files, and direct helpers such as SYSTEM, TITLE, and APPEND_SYSTEM remain effective discovery inputs and are rejected unless permitted. Checks include actual HOME, managed and active-profile configuration roots, agent roots, and mode-specific dotenv files selected by effective `NODE_ENV`. Diagnostics identify source categories and nonsecret paths without reading configuration bodies merely to detect their existence.

To enable project skills or project MCP, add this to the private profile override:

```toml
[overrides.profiles.omp-kernel.agent_options.discovery]
project_resources = true
project_roots = ["/absolute/project"]
```

This permits only validated skills and MCP within declared roots. Final link targets, content, and secret boundaries remain checked. Project rules, extensions, prompts, settings, authentication, and identity overrides remain prohibited. A policy/root change requires `apply`; actual sources are checked again before each spawn. This is a configuration boundary, not an operating-system sandbox.

Native skill discovery walks `.omp/skills` from cwd through ancestors. Native project MCP reads only cwd's `.omp/mcp.json` or `.omp/.mcp.json`; having both is ambiguous. Declaring a root does not stop checks above it. Project MCP accepts credential-free HTTPS or an exactly locked Python interpreter and echo script with absolute command paths. It rejects environment/header/auth/OAuth/cwd overrides and environment placeholders. Use managed declarations for credentials and executables requiring dependency management. Project resources stay read-only; reports contain paths and digests.

The daily recipe is documented in [omp-kernel](omp-kernel.md). Additional profiles must be registered in public `profiles/` before private overrides can select them. A different local file, machine, or state root cannot take over an existing physical instance; ownership conflicts return 4.

## Lifecycle and concurrency

`validate` and `render` construct candidate identities and configuration intent. An initial `plan` can compare empty state without an installed runtime or deployed binding. Initial `apply` persists the identity. `run`, `capture`, `rollback`, and managed `usage` require the deployed identity.

The physical-instance lock is acquired before the management-state lock. Managed `run` and `usage` hold shared leases until their child exits, allowing multiple foreground sessions for one profile. Configuration operations such as `apply`, `rollback`, and `capture` require an exclusive lease and return 4 while sessions are active. The manager never terminates sessions to obtain a write lease. Concurrent sessions share native HOME/profile; avoid resuming or editing the same session in two processes.

When a configuration transaction is pending, resolve the reported conflict and use explicit `apply` or `rollback` to recover that instance. `recover pi` handles Pi execution leases and does not apply to OMP. See [testing](testing.md) for the limits of historical parallel-session evidence.
