# 能力、默认体验与验收规划

临时设计材料：仅用于开发分支讨论；合入 `main` 前必须删除，或整合到正式文档后移除本临时文件。本地提交不代表设计已采纳或产品已验收。

状态：目标能力。以下“提供/启用”描述拟交付产品，不表示当前 checkout 已有实现或验证。所有真实宿主、插件、服务和平台验收目前未执行。

## 2. 日常体验与场景

### 场景 A：解释代码或修改一个配置

主 agent 读取必要文件，直接回答或修改；做与风险匹配的检查。默认不创建 worktree、计划文件、Todo、子代理或审查轮次。完成报告包含实际变更、验证与限制。

成功条件：相比原生 Pi 不新增强制确认或流程，资源发现与工具行为可解释。受管部署和发布操作已有的真实授权边界仍保留。

### 场景 B：定位复杂故障

主 agent 可调用系统化调试 Skill；需要并行时派 scout 收集调用链/日志证据，自己判断根因。使用测试验证修复假设，达到任务目标后停止，无新证据不反复全量审查。

成功条件：调查、假设、修复与验证能对应；子代理不接触无关私有文件；失败不会变成主会话无限自动续跑。

### 场景 C：多文件功能开发

先形成足够执行的计划；由主 agent 分配有文件所有权的 worker，独立 reviewer 在写入完成后审查稳定 diff。模型角色绑定独立配置，复杂事务、锁、日志和恢复语义由主 agent 决定。

成功条件：并发上限明确、无重叠写入、实际检查留证、已知失败不伪装通过。需要人类决定时才中断，其它任务自主推进。

### 场景 D：查询库API并完成实现

启用文档模块后，先核对项目实际依赖版本，再用 Context7 或官方文档查证，引用具体文档来源。查不到时明确说明，不用其它版本示例冒充当前API。

成功条件：所用接口与锁定库版本匹配，服务不可用能清楚返回；未配置模块时基本编码能力仍可独立交付。

### 场景 E：验证网页功能

启用 browser 模块，在专用命名会话内操作项目测试页面、读取结构和截图。页面状态与个人日常浏览器分开；需要个人账号时独立明确授权与归属。

成功条件：能重现指定交互，结果与截图可定位，退出不任意关闭用户其它浏览器。浏览器本身、MCP或CLI的状态删除与配置rollback分别处理。

### 场景 F：长任务交接

任务文件记录剩余工作、已完成变更、验证命令、失败与环境不足。用 Pi 原生会话继续或新会话读取交接；不承诺重启后恢复所有后台进程。

成功条件：无需复制完整对话即可继续关键工作；交接资料不包含凭据、私人端点和非必要会话正文。

## 3. 角色与工具范围

| 角色 | 任务 | 初始工具选择 | 写入约束 |
| --- | --- | --- | --- |
| 主 agent | 分解、取舍、关键判断和验收 | 项目需要的原生工具与选中模块 | 按用户授权，整合任务结果 |
| scout | 搜索文件、定位调用链、收集证据 | 优先 read/grep/find/ls，必要时选定只读外部工具 | 默认不写项目文件 |
| worker | 已决定方案的有边界实现与验证 | 必要读写/shell工具 | 明确拥有文件与目录 |
| reviewer | 审查稳定diff、验证关键不变量 | 优先读取与diff检查工具 | 默认只报问题，不与worker并发改同文件 |

角色名称和工具范围是设计目标，具体配置按最终插件格式编码，不能把一个候选的 frontmatter 直接套给另一候选。没有验证的工具 allowlist 或提示规则不构成强制文件系统只读。若给 scout shell，必须说明其权限边界；不能仅按角色名称称其无写入能力。

子执行可以继承同一 profile 的 agent directory，独立保存子会话与结果；没有要求每个子任务拥有新账号。父子是否共享原生认证与资源必须说明并验证，不为制造隔离而复制 auth 文件。

## 4. 精选资源与触发方式

| 资源 | 触发 | 预期产物 | 默认不要求 |
| --- | --- | --- | --- |
| plan 提示模板 | 复杂任务或用户要求 | 目标、任务、依赖、验证和风险 | 每个简单任务写计划 |
| review 提示模板 | 有稳定改动可审查 | 按严重程度列出可行动问题 | 额外修改或重复全量审查 |
| test/verify 提示模板 | 变更需要验证 | 实际argv、退出码、结果及限制 | 为低影响可逆编辑机械增测 |
| handoff 提示模板 | 长任务切换/交接 | 当前状态、证据、下一步 | 保存整段会话 |
| systematic-debugging Skill | 根因不清楚的故障 | 可证伪假设与最小验证 | 无边界反复尝试 |
| verification-before-completion Skill | 准备宣称完成 | 结果与证据对应 | 把README/CI存在当通过 |
| writing-plans Skill | 需要详细执行计划 | 路径、任务包和验收 | 全局自动强制工作流 |
| 其它方法型审查 Skill | 项目或用户需要 | 与实际工具相容的审查记录 | 默认引入完整引导扩展 |

名称表示选取方向，最终路径/版本、相对引用、许可和工具映射在实施准入时确认。上游Skill的要求若与用户指令或仓库规则冲突，不能不加判断地全盘加载；应缩小精选范围或不采用，不默认修改上游Skill内容。

## 5. 失败与降级

| 失败 | 预期处理 | 不能声称的结果 |
| --- | --- | --- |
| 缺运行包/完整锁不匹配 | 管理器按契约拒绝，提示显式sync/lock维护 | 不边启动边安装 |
| 明确需要的SecretRef缺失 | 返回凭据缺失；用户修复或禁用对应模块 | 不静默换提供方或读取其它宿主认证 |
| 原生OAuth未登录 | 按Pi原生登录流程处理，账号归当前实例 | 不由doctor自动登录 |
| MCP连接失败 | 展示失败服务和非秘密原因；保留其它能力真实状态 | 不以配置存在称服务可用 |
| 子代理失败 | 返回任务失败和已产生变更，由主agent决策 | 不自动无限重试或无限递归 |
| 子代理插件不兼容 | 冻结pro或显式切换已验证组合；base独立可交付 | 不修改缓存、vendor或宿主源码 |
| 浏览器依赖不足 | browser模块未就绪，记录平台/依赖缺口 | 不将CLI帮助能运行当浏览器验收 |
| 维护发现活动/未知实例 | 阻止不安全维护，走显式恢复 | 不终止用户进程获取锁 |
| 原生进程返回非零 | 交互启动成功后保留原生退出码 | 不把原生退出码重新解释成管理器错误类别 |

基础配方与高阶配方的账号、锁、状态彼此独立；pro模块缺凭据不影响另一个base实例。对同一配方已启用的必需模块，不能通过静默忽略来掩盖缺失配置。

## 6. 维护与性能评价

记录而不预设改善百分比：冷/热启动、额外进程、插件与工具磁盘占用、首轮上下文、完成同任务的用量、结果文件大小、失败信息和卸载步骤。模型、任务、网络与缓存条件应相同；上游宣传数字只作研究线索。

base的目标是消除第三方扩展与服务的默认启动负担。pro只为实际启用的能力支付开销；按需暴露工具不会自动消除服务连接成本。没有真实测量前不写“更快”“更省token”或稳定性百分比。

## 7. 交付等级

| 等级 | 含义 |
| --- | --- |
| 研究候选 | 一手资料存在，价值与风险已比较 |
| 静态契约确认 | 指定版本的入口、参数、来源、许可证与依赖已核对 |
| 隔离检查通过 | 管理器配置、锁、部署和失败路径通过默认隔离测试 |
| 原生组合验收 | 获明确授权后，指定宿主/插件/平台实际加载和操作通过 |
| 账号场景验收 | 获对应授权后，指定服务/模型账号场景通过 |

本轮资料处于研究候选与部分静态接口核对阶段。任何平台支持、真实模型调用或安全隔离声明都要绑定后续证据，不因文档已完成自动晋级。
