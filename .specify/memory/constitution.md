# rotom Constitution

## Core Principles

### I. 公共核心与真实原生适配

- `./agentcfg` 必须统一管理公共配置来源、机器覆盖、原生转换、依赖、部署与启动。
  公共 registry、rules、skills 和 profiles 表达共享意图；工具专属路径、字段、认证映射
  和包管理细节必须由适配器及依赖后端处理，不得将 DSH、Pi 或 OMP 特例塞回公共配置模型。
- 新接入或重建必须先盘点 DSH/OMP 的公共契约与实现差异。配置校验、合并与渲染、
  完整依赖治理、部署所有权、配置恢复和实例运行准入的中性实现必须通过公共模块共用，
  不得为 Pi 复制第三套公共管理逻辑，也不得仅为保留旧实现将 Pi 专属执行平台改称公共模块。
  原生目录、配置投影、包格式和生命周期差异使用薄适配；共用不要求相同锁格式或安装器。
- 框架输入必须严格校验 schema、引用及能力。未知字段、无效引用、未声明覆盖和未支持
  能力必须失败，禁止静默丢弃、修复或编造映射。非受管原生字段必须保留。
- 分层合并必须递归合并对象、整体替换数组，并保留空数组和 `false` 的明确含义。
  仅显式声明的文本模板允许求值；结构化 JSON/YAML 必须使用序列化器。
- 当前已实现 DSH 与 `ccch1mneyyy/dsh-TUI`、Pi 和 OMP 适配器。实现存在、历史验收
  与当前版本可部署性必须分别判断；应按当前源码、完整锁及对应范围的验收证据判断，
  不能沿用历史通过结论。
  Codex 是认证路由或官方 CLI 委托，不是独立配置适配器。其他宿主仍需独立实现与验收。

理由：统一管理必须建立在真实能力和稳定契约之上，不能把收录目录或测试替身当作宿主支持。

### II. 秘密隔离与明确所有权

- 公共配置来源进入 Git，机器覆盖和秘密保留在仓库外；禁止提交 secrets 或凭据。
  SecretStore 必须与普通配置分离，秘密值不得进入通用配置、渲染产物、摘要、日志、
  异常、快照或配置备份。启动时才按已部署引用解析所需秘密并按需注入。
- 原生 OAuth、登录数据、trust、会话及运行日志必须与受管配置区分。
  capture 只能读取明确 allowlist，生成经过校验的非秘密覆盖提案，不能全量导出原生状态。
- 工具/profile 必须各有隔离实例、状态、上一版备份和活动锁，并保持原生 home 身份稳定。
  不得默认接管 `~/.dsh`、`~/.pi/agent` 或其他工具账号目录，也不得因更新 Pi 改写 DSH 状态。
- 私人本地文件必须为当前用户所有的普通文件，权限为 `0600`，私人目录为 `0700`。
  写入必须验证路径祖先、所有权和链接边界并在写前复查；禁止放宽保护或自动接管非空目录
  来绕过冲突。读取可信公共来源与写入私人目标必须采用各自的权限边界。

理由：管理器只能修改声明拥有的配置，账号、秘密和非受管数据必须保持独立。

### III. 确定性部署与可恢复状态

- 渲染必须从已校验的非秘密输入生成确定性字节或字段意图，不读取当前原生配置来构造
  期望整文件；部署阶段负责基线、当前值和期望值的三方比较。
- 当前值等于基线时允许更新；期望值等于基线时保留并报告原生漂移；当前值等于期望值
  时不重写；双方均修改且结果不同时必须报告冲突。保留漂移不得自动接纳为新基线。
- 整文件或字段所有权冲突、重叠 selector、活动实例或恢复待处理必须阻止不安全写入。
  管理器不得通过终止用户进程获取写入权限。
- 单文件写入必须使用同目录临时文件与原子替换；多文件变更必须提供 pending 恢复记录、
  失败恢复和冲突复查，不得宣称跨文件或外部进程的绝对原子性。
- 每次成功且有实际变更的部署只保留上一轮受管配置备份。无变化或失败不得轮换备份；
  成功 rollback 必须消费备份，不得删除新增非受管数据。配置回滚不包含软件降级或数据库迁移。
- 配置部署的 pending/rollback、实例运行与维护准入、任务/子代理执行恢复必须分别声明范围。
  前两者遵守公共契约；不得将旧 Pi 任务数据库、监督进程或执行租约当作必须保留的公共恢复层。
  会话恢复、取消请求及父进程退出不能单独证明文件副作用已撤销、后代进程已退出或任务成功；
  无法确认时必须报告未知，阻止相关不安全维护，不得据此自动重放有副作用的工具调用。

理由：重复同步、用户原生修改和中断恢复必须有可解释的结果，不能依靠覆盖用户状态完成部署。

### IV. 显式副作用与可复现依赖

- 入口必须使用已准备的仓库 `.venv`，不得通过 `uv run` 或无版本 `npx` 隐式安装。
  `validate`、`render`、`plan`、`apply` 和默认 `doctor` 必须离线运行。
- `lock` 显式解析完整依赖锁；`sync` 只消费现有锁安装或修复运行包，不更新锁、启动宿主
  或登录；`apply` 负责部署，不安装依赖；`run` 使用已部署契约，不得隐式 sync/apply。
  `doctor --live` 只检查声明服务的可达性，不得自动登录或调用模型。
- 远程依赖必须记录版本、来源、不可变提交或完整性信息及完整依赖锁；本地插件必须记录
  来源及内容身份，保留必要构建输入和运行资源。vendor 来源和变更必须可追溯；
  agent 上游源码不得修改，遵守第六项原则。
- 安装或修复必须暂存并验证成功后再激活，保留实例账号 home。运行包检查必须核验声明的
  目录形状、链接、包清单和必要入口，不能仅凭 marker、文件大小或时间戳替代正文验证。
- Pi 迁移或退役重建不得将旧流程中的“生成后自动安装缺失包”引入 render/apply/run，
  必须核对宿主的项目资源发现与自动安装行为，不能只检查管理器入口。
  新方案的运行与维护不得依赖旧 Neovim 同步模块或 `starter` 的本机绝对路径。

理由：配置、安装、部署和启动有不同副作用，必须可以独立审阅、执行和复现。

### V. 默认隔离测试与可核实证据

- 默认测试只允许仓库内和临时 HOME 目录，必须使用临时 HOME/DSH_HOME/XDG、网络阻断、
  假子进程、虚构 provider/model 和文件哨兵。Pi 测试还必须隔离其原生配置与资源发现路径。
- 默认测试不得启动 DSH、Pi、Codex 等第三方宿主。真实 smoke 必须作为独立显式步骤，
  获得用户明确授权后执行；真实账号登录或模型调用必须有对应的独立授权。
- 配置契约、秘密边界、部署、恢复和依赖行为变更必须有覆盖相关风险的隔离验证，
  包括冲突及失败路径。Pi 接入或重建、公共模块变更必须覆盖受影响的 DSH/OMP 契约，
  并验证不同工具/profile 间的状态隔离；不得将未受影响范围的历史通过冒充本轮回归证据。
- 验收必须记录实际命令、环境、结果和未覆盖范围。测试文件存在、任务勾选、CI 文件
  已配置或第三方进程退出 `0` 均不能单独代表功能通过。
- 无账号 smoke 不能替代真实账号调用证据；Linux 本机通过不能推定 macOS 或远端 CI 通过。
  未执行、失败和通过必须分别报告，不得关闭保护来制造通过结果。

理由：默认验证必须可安全重复，支持声明必须由实际行为证据证明。

### VI. 不修改任何 agent 的上游源码

- 本项目是配置与扩展管理器，不维护 agent 宿主的功能补丁或自有 fork。
  DSH、Pi、OMP、委托使用的 Codex CLI，以及以后接入的所有 agent 均遵守此约束。
- 集成仅使用官方配置、公开插件/扩展 API、官方 CLI 和仓库自有适配代码。
  可以编写独立本地插件；不得修改 agent 上游源码、vendor/缓存中的宿主副本或官方二进制，
  不得通过补丁重编译、运行时 monkey patch 或调用私有实现接缝改变宿主行为。
  按官方流程构建未改动的上游源码不构成功能补丁，仍须满足锁、来源和显式副作用要求。
- 官方能力不足时必须如实报告限制，并调整功能范围、设计纯插件替代或等待上游支持。
  不得以某个 spec 已批准、历史测试已通过或保持旧功能为由豁免本原则。
- 生效前的宿主补丁和验收记录只作为历史与迁移依据，不得新增、扩展或继续构建发布。
  当前仍使用旧方案的部署必须明确标记待迁移，不能将原则记录冒充迁移已完成。
  切回官方运行包必须保护账号、凭据、会话和受管配置的恢复边界，不自动停止用户活动实例。
- 每次接入、升级、规格/计划审查均须核对是否修改宿主源码及是否使用公开接口。
  历史偏离须登记具体范围、当前状态和迁移任务；此原则不授权顺带删除历史证据或迁移其它工具。

理由：避免承担第三方宿主源码维护、补丁兼容和自编译分发成本，使功能可以随官方版本升级。

### VII. 公开隐私与明确提交身份

- 公开代码、文档、提交消息及报告不得包含真实用户名、私人绝对路径或业务路径、主机元数据、
  个人邮箱、认证链接/验证码、token、密钥、会话正文或私有端点；使用通用路径、保留域名
  和虚构测试数据。必须保留法定许可、上游署名、公开来源标识和必要工具链事实。
- 公开检查不得读取真实密钥、认证或会话文件；命中仅记录脱敏位置、类别及状态，不输出原值。
  修复备份须在公开仓库外私人存储，目录 `0700`、文件 `0600`。确认凭据泄露时由所有者
  先撤销或轮换；清理及有限扫描均不能证明从未暴露凭据。
- 提交仅使用用户明确批准的公开身份，包括批准的 noreply 或 bot 身份。`user.name`、
  `user.email`、`user.useConfigOnly=true` 仅设于仓库本地 Git 配置；共享规则不得固定真人
  姓名或邮箱。每次提交前核对本地配置、作者与提交者实际身份和环境覆盖，二者均须匹配
  批准身份；缺失或不一致必须解决，不得继承全局值或系统自动推导身份。

理由：公开隐私边界包括内容与 Git 元数据，不能只清理当前文件或只设置未来作者默认值。

### VIII. 所有工作树合并门禁与历史切换

- 每个分支与工作树合入 `main` 前，必须盘点目标 `main`、候选 HEAD、工作区状态与文件
  所有权；审阅最终差异、私密信息、作者/提交者及将引入的历史、来源/依赖/锁一致性，
  执行与范围匹配的隔离、原生和平台验证。不得丢弃其他代理或用户工作来获得干净候选。
- 验收记录必须绑定候选、目标、锁、实际 argv、环境类别、退出码及脱敏证据；任务状态区分
  已完成、进行中、失败待决策、环境不足未验证。未验证不是通过，环境不足不自动阻塞无关
  工作；已知失败须修复或取得明确范围接受，不能默默豁免。
- 所有写入完成后针对稳定最终差异或提交审查；后续修改重跑受影响检查。目标 `main` 前进
  时重新评估差异、历史及证据。仅在授权范围内快进或合入已审阅合并，不强推或丢弃用户工作。
- 历史清理只作用于明确授权引用；仅清理 `main` 不代表全仓库擦除，保留的私人分支、工作树
  和备份仍可能含旧历史。旧谱系不得普通合并回干净 `main`，须从干净 `main` 重放自身变更，
  谨慎挑选提交、规范化身份并重做全部适用门禁。仅合入新 `main` 或祖先检查通过不能证明
  其它旧父提交已清理；远端更新须单独授权。

理由：所有来源的工作进入主线时须满足相同验收，避免旧历史重新引入已移除的私密信息。

### IX. 社区选型与版本证据

- 社区热度用于发现候选，不能代替能力、兼容性或安全证据。选型必须比较官方原生能力、
  公开扩展与必要自有适配，记录收益、维护成本、重叠职责、来源许可和退出方案；
  默认组合不得仅因热门而增加插件，同类能力必须明确配置、数据及进程的所有者。
- 版本适配必须记录核对日期、精确宿主与插件版本、来源身份、配置依据和平台范围。
  新候选及升级须核对当时官方稳定版本；采用旧版本必须说明原因与兼容边界，
  不得用浮动 latest/main 或新版发布代替兼容验证，也不得把旧版本问题自动归于新版本。
- 具体插件、版本号、配置键和值保留在规格、设计与锁中，不固化为宪章义务。
  原生设置、扩展设置、机器绑定、项目资源和认证/会话状态必须分别标明归属、校验及发现范围。
  原生 schema 允许扩展字段不豁免框架输入的未知字段拒绝；非受管原生字段仍须保留。
- 选型必须核对精确发布物及其实际使用的公开接口，遵守第六项原则。
  关闭显示或某项功能不能证明插件已停止使用私有接口；接口不满足时必须暂停准入、
  降低范围或更换候选，不以信息量、旧功能或社区流行程度豁免。
- 文档与源码审阅、静态配置校验、隔离测试和原生组合验收必须分别记录。
  配置意图不得写成已部署或已通过；请求的模型、宿主选择和可核实的实际执行模型必须区分。
  无证据的数据必须标为未知或不可用，不能显示为零、成功或已确认。

理由：社区方案提供候选与经验，仓库支持承诺必须建立在固定版本、公开接口和实际证据上。

## 技术与迁移约束

- 管理器使用 Python 3.11+ 与 `uv`，依赖基线为 PyYAML、jsonschema、Jinja2、pytest。
  registry/profiles/local 使用 TOML，DSH 原生产物使用 YAML；Pi 原生格式必须在适配器中
  明确编码与校验，不改变公共配置格式，也不要求把 Pi 插件改写成 Python。
- Python 代码使用双引号字符串、2 空格缩进和中文注释。提交必须原子化，采用
  Conventional Commits；依赖变更必须同步锁文件并审阅来源。
- `src/agentcfg/` 存放公共实现，`shared/` 存放公共内容，`profiles/` 存放配方，
  `agents/<id>/` 和 `locks/<id>/` 隔离宿主资料与依赖，`schemas/`、`examples/`、
  `tests/`、`docs/` 分别保存 schema、虚构示例、测试和文档。
- Pi 重建以整套旧集成退役为目标：Pi 专属实现、配方、插件、锁和测试必须逐项审视，
  明确替代、重建或删除，不以保持旧功能完整为默认目标；公共部分按第一项原则对齐并共用。
  删除前必须盘点文件引用、公共消费者和历史状态归属，不能仅按文件名前缀批量移除。
  原仓库、`/path/to/starter` 和下载方案均属来源材料，不能直接成为新契约或通过证据。
  盘点须覆盖配置同步、skills、extensions/packages、远程包、prompts、themes、agents
  及关联行为，记录每项取舍与理由，不得把旧文档数量当作完整清单。
- 新 Pi 以 Base/Pro 分层重建：Base 必须能独立使用，Pro 仅加入经准入的增量能力；
  两者共用公共配置逻辑、资源及运行包来源，正常使用同一宿主版本，分别保有完整锁与实例状态。
  高阶组合适配不足不得阻塞 Base；共用来源不得导致共享秘密、会话、缓存或进程所有权。
  主宿主采用未修改的官方 CLI 与公开扩展接口，不恢复旧 Pi 自有任务执行平台。
- 被选中迁入的技能必须保留完整 SKILL.md 包、脚本、资源、相对引用和必要执行权限；
  插件必须保留入口、清单、依赖和来源说明。复制与渲染不得执行技能脚本或加载插件。
  公共资源同源引用，工具特定接入保持薄适配，不重复引入已有规划流程或重叠管理器。
- 新规格必须明确旧字段合并、资源删除、备份及安装行为的去向，以及新 agentcfg 契约。
  旧来源目录不能默认删除或改写；仓库内旧 Pi 代码的退役不能自动删除用户原生状态。
  切换受管目标前必须提供可审阅差异、冲突处理与恢复方案，避免两个管理器同时写同一目标。
  运行缓存、认证、会话和历史备份不作为公共配置资源迁入。验收须核对声明资源与实际发现结果。
- Pi 状态栏选型必须以原自建栏的信息需求作对照，逐项记录数据含义、来源、缺口、
  降级显示及窄屏行为；信息量目标不能成为使用私有接口或伪造状态的理由。
  未经准入的候选配置只能标为条件设计，不能进入默认配方或被称为已适配。
- CLI 必须保持以下退出码契约；成功启动原生进程后必须保留其退出码。

| 退出码 | 管理器语义 |
|---|---|
| 0 | 成功，可包含漂移或待登录提示 |
| 2 | 参数、配置或锁校验错误 |
| 3 | 所需凭据缺失 |
| 4 | 所有权冲突、活动实例或恢复待处理 |
| 5 | 依赖或原生检查失败，或缺少必要运行包 |
| 6 | 文件系统或内部操作失败 |

## 开发与审查流程

1. 规格与计划必须明确配置来源、受管范围、命令副作用、秘密流向、失败行为及验收边界，
   并在 Constitution Check 中核对适用原则；无关项必须注明理由。
2. Pi 重建必须先形成旧集成退役清单、来源到目标的资源/行为映射与 DSH/OMP 公共差异矩阵，
   再确定新 Pi 薄适配、Base 和 Pro 的实施边界。旧实现和文档只能作为调查依据，
   对相互矛盾的描述必须核对代码与隔离测试，不能直接将旧行为认定为新框架契约。
3. 实现审查必须核对未知字段拒绝、秘密隔离、所有权冲突、恢复、退出码及文档一致性；
   依赖升级还必须审阅完整锁、vendor 差异和来源，记录工具链与平台验证范围。
4. 合并前必须提供与风险相称的检查证据，记录未执行项及原因。文档变更可使用结构、
   链接和差异检查；涉及第三方宿主或真实账号的验收仍受第五项原则约束。
5. 宿主或插件选型、升级及默认配置调整须按第九项原则记录证据与未满足项。
   新规格必须明确替代哪些旧要求；宪章修订、设计文档和旧测试存在均不代表实现或迁移已完成。

## Governance

- 本宪章是项目规格、计划、实现与审查的治理基线；`AGENTS.md` 提供日常工程约定，

- 版本采用语义化规则：删除或不兼容重定义原则升 MAJOR；新增原则或章节、实质扩展要求
  升 MINOR；不改变语义的澄清、措辞和拼写修复升 PATCH。`1.0.0` 为首次建立的规则。
  `2.0.0` 于 2026-09-30 按维护者要求新增第六项原则，并收紧既有 vendor 修改约束；

- 每份规格、计划和实现审查必须核对本宪章。已知偏离必须记录具体条款、理由、影响及修复
  或迁移安排；不兼容变更必须先修订宪章，不能只用任务备注豁免原则。
