# C++ 修改前的局部证据

<!-- 来源：本仓库按 rotom 的大型 C++ 局部检索需求原创；非外部技能的转载。 -->

只读取任务相关定义、声明和最短调用链；下表是需要回答的问题，不是全仓库审计清单。

| 边界 | 从哪里取得证据 | 修改前确认 |
| --- | --- | --- |
| 所有权与生命周期 | 类声明、构造/析构、创建点、实际调用者 | 谁拥有对象，指针/引用是否借用，move 后状态，回调捕获与异步存活期，RAII 清理是否覆盖失败路径 |
| 并发 | 调用线程、锁的获取/释放处、共享状态读写点 | 锁顺序，临界区是否跨回调/等待，条件变量谓词，取消和关闭顺序，原子内存序所依赖的 happens-before |
| 事务与失败恢复 | begin/commit/abort 的局部实现及调用点 | 提交点、状态转换、失败前后不变量、回滚拥有的范围、重试是否幂等、异常/错误码是否遗漏清理 |
| 编译与测试 | 模块构建文件、相邻测试、已有编译数据库中的相关条目 | 宏、平台分支、模板实例与实际构建目标；不要凭另一平台或未实例化模板断言可用 |

## 示例：提交回调疑似悬空引用

用户指向 storage 模块的 `Transaction::Commit`：先读声明及实现的提交段，标记回调保存位置与提交点。若发现捕获 `this`，只追“谁创建 Transaction → 谁注册回调 → 谁调度/取消 → 谁销毁”的链条。

不能只把引用改成 `shared_ptr`：先核对是否形成循环引用、销毁是否必须发生在特定线程，以及 abort 后回调能否继续访问已撤销状态。不能为消除死锁直接删锁或移出事务：先记录锁保护的不变量与失败后的状态。

证据记录应包含真实文件位置、观察到的顺序、仍未知的调用关系及针对性测试。若文本调用链因虚调用/模板无法确认，先利用已有编译上下文的局部语义查询；没有上下文则报告缺口，提出需授权的最小构建或索引范围。

验证只运行已授权的模块目标与测试；不启动第三方宿主、不默认全量编译、不把搜索命中或代码审读描述成测试通过。
