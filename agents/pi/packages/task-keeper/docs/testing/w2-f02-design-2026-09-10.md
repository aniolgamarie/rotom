# W2/F02 最小实施设计（已实现，完整验收待收口）

原依据：D4、Shared write resource exclusion、SCH-009/TK05/TK06和任务8.4。仅补可信共享目录声明到现有调度资源的连接；不改变同state root协调范围。

## 配置与身份

在已有用户可信`verificationBindings.<checkId>`增加可选`sharedMutableDirectories: string[]`。每项为当前环境提供的绝对目录路径；项目配置仍不允许提交verificationBindings。未声明时保持已有行为。

对固定workflow实际使用的checks解析存在的真实目录，canonical realpath去重，生成容量1/单位1的`shared-directory-<digest>`。缺失/非目录/相对路径在提交阶段拒绝，不能为了生成锁创建目标目录。用户声明同一共享根的别名应得到同一个resource ID。相互重叠的不同根不自动推断为同一资源；配置应使用共同共享根。

## 单一执行路径

1. `TaskService.submit`在持久job/工作区前解析并绑定目录身份。
2. `fixedWorkflowPlan`接受已解析资源映射，保持纯编译函数；verification step追加对应check的资源，writer追加所有适用checks共享目录资源的去重集合。
3. `Scheduler.next/dispatch → Store.prepare`使用原有整组原子预留。等待者不持局部新资源；同目录不同job不可同时运行；独立目录可继续。
4. 创建工作区后、每次真正派发前，重新核对声明指向的canonical身份与job冻结身份。不允许路径别名变更后悄悄拿旧锁访问新目录；变更应阻塞并说明。资源身份进入状态/诊断；不要把未声明文件访问声称为已协调。
5. 原有终止/unknown规则决定释放，不能因超时、owner失联或仅有终态字符串释放未知writer。声明本身不授予child写外部目录的工具权限。

本功能只管理可信参与者显式声明的相同目录资源；不会阻止插件外的程序修改它，也不新增完整文件系统沙箱或跨机器锁。部署配置不得让可信命令运行期间被其它程序重新指向不同共享根。

## 验收与复用

- 扩展配置/固定计划检查：字段可选、项目不能改、writer/verify对应、去重、空声明兼容。
- 复用Store/Scheduler资源竞争夹具：两job以别名请求同共享目录，正反顺序下仅一个获整组许可，unknown不释放，确认解除后另一个可继续，独立目录不阻塞。
- 复用真实workflow/verifier夹具：接收端或实际验证命令的持有/释放barrier，验证声明确实到达资源表；命令与managed writer竞争时没有冲突写入；路径变更在执行前拒绝。
- 不按每个配置项复制所有验证层，不新增矩阵分母。只有所需predicate与observer齐全才关闭F02；本设计文档本身不是实现证据。

## 实施记录

已按上述连接实现。`sharedWriteResources`按check冻结到ManagedJob，status显示实际资源ID；`admitted`在真正调用前重新核对，receipt检查也会因绑定漂移失效。原有无声明job用空映射兼容。

新增4条针对F02的回归：一条状态/计划契约、一个双进程竞争变体、两个真实Pi workflow变体。已有资源夹具继续复用，没有新建调度或覆盖率框架。

- 状态检查覆盖别名去重、writer/verify两个竞争顺序、unknown保留、确认释放、独立目录、非法/缺失路径和项目拒绝改写绑定。
- 两个真实父进程声明同一根的别名，只有一个写入effects；未知占用不放行，确认原进程死亡后另一个继续。
- 实际Pi fix先等待外部进程持有的共享目录；验证命令尚未执行。确认释放后，baseline、writer、最终构建/测试和required review完成，writer实际请求时有属于该job的write intent共享占用。验证命令在声明目录的两个写入记录保留。
- 在实际baseline执行中把声明别名改向另一目录后，后续动作以SHARED_DIRECTORY_BINDING_CHANGED阻塞，零子模型请求/写入，用户主树保留。
- 独立负向控制仅在测试副本移除writer追加共享资源的一行；实际workflow断言检测到writer请求时共享claim为0（期望1）。测试副本、manifest与失败运行保留在`test-results/shared-writer-negative-control/`；不是生产变更，也不提供正向验收信用。

完整运行与源码锁见当前continuation记录。未把上述证据视为任意文件系统/所有矩阵的认证。

证据边界：新增真实Pi场景证明verifier等待已有writer及后续writer持锁，对应SCH-009/TK05。TK06要求的“verifier先冻结，另一writer竞争”目前只在S检查双向资源行为；本场景不借用TK06的E信用，该方向的完整产品观察仍归W4。
