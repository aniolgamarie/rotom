# Feature Specification: Pi 双 Profile 长期交付

**Feature Branch**: `feat/pi-toolkit-upgrade`

**Created**: 2026-10-04

**Status**: 实施中；正式规格已整理，阶段组件与授权探针分别验收，不代表产品已部署或全部验收通过。

**Input**: 用户要求交付可长期维护的 `pi-base` 与 `pi-full`，共享日常工程能力，具备真实资源隔离、可选模型风险审批、有限协作与持久只读任务；当前 Linux 环境必需，其他平台按需。依据为 2026-10-03 讨论包 `rotom-pi-two-profiles-codex.zip`（SHA-256：`b6b59af7ca8329d23b336a07995309f47bf291aa86886be7e422f9388d6ac46d`）及 2026-10-04 会话补充。本文与关联文档自包含，无须重新上传讨论包。

本任务取代旧方案“基础必须带子代理、只能一个生产 profile、必须保留全部旧行为”的产品约束，不改变已关闭的 `001-unify-pi-capabilities` 历史范围及结果。优先级为当前用户决定、AGENTS.md/宪章、本文、历史讨论。

来源范围：本任务升级已迁入 agentcfg 的 Pi。starter 的既有资源与行为映射沿用 [001 来源调查](../001-unify-pi-capabilities/source-inventory.md)、[最终资源清单](../../agents/pi/migration/resource-manifest.json)、[逐项能力处置](../../agents/pi/migration/capabilities.toml) 及 [001 关闭报告](../../docs/acceptance/pi-spec-closure-20260924/README.md)；初始调查不能代替最终清单。本轮按 [research.md D16](research.md#d16-迁移来源基线与本次升级差量) 核对配置同步、skills、本地扩展、远程包、prompts/themes/agents 等资源在新版本和两profile中的保留、替代或排除，以及合并、删除、备份和安装行为的变化。T002记录逐项差量与理由，不重新迁移或改写starter；历史通过不作为新组合的支持证据（R01、R02、R08、R31、R37）。

## Clarifications

### Session 2026-10-06

- Q: 默认模型的 tokenizer 只有估算，发送前严格输入上界尚未验证时如何处理自动审核？ → A: 用户选择保留严格上限，计量未验证前关闭自动审核；其他可实现的接线继续。不接受估算误差或重新定义预算语义，也不把关闭态替代启用态的必需验收。

## User Scenarios & Testing *(mandatory)*

以下 US1–US7 与既有任务保持对应。优先级规定依赖顺序，不降低 P2 的最终必需性；Base 是可独立使用的中间交付，完整任务必须继续交付 Full。

### User Story 1 - 单主 Agent 日常开发（US1） (Priority: P1)

用户希望只用一个主 Agent 完成日常工程任务，无需安装或启动协作服务，仍能搜索、编辑、测试、查看差异并恢复会话。

**Why this priority**: 日常开发是两个 profile 的共同价值，也是 Base 能独立使用的基础。

**Independent Test**: 冷安装 Base，移除 Full 专属依赖和服务，在合成 C++ 项目复现并修复 bug，再完成 Shell/Neovim 小任务；分别核对主会话认证与会话恢复。验收对应 S03–S07、S09–S14、B01–B06（完整 Base gate 还需 US2 及 US7 对 Base 适用的维护证据）。

**Acceptance Scenarios**:

1. **Given** Base 已冷安装且没有 Full 依赖或服务，**When** 用户要求修复合成 C++ bug，**Then** 主 Agent 先复现问题、完成最小修改、执行相关测试并提供 diff，不强制委派。
2. **Given** 用户已授权工作区中的 Shell/Neovim 小任务，**When** 用户直接提出任务或运行可组合的长命令，**Then** 可完成操作并查看日志、退出码、超时、取消和实际停止状态，无需逐条登记 Shell 组合。
3. **Given** 用户已登录 Pi 主会话并保存会话，**When** 手动切换模型、重启和恢复，**Then** 登录权限与工具调用可核验，用户限制、失败证据和未完成任务引用保留，Base 不要求 Codex 安装或登录。

### User Story 2 - 可解释的权限与执行隔离（US2） (Priority: P1)

用户希望已授权的日常编辑和测试顺畅完成，同时知道操作在哪里受保护、哪些入口尚未被隔离，并能依赖实际越界阻断。

**Why this priority**: 真实的受管执行边界是安全使用两个 profile 的前提，不能由界面提示替代。

**Independent Test**: 在当前 Linux 的真实受管 Shell/子进程与文件入口分别执行允许操作和越界操作，核对保护模式、覆盖矩阵及隔离不可用行为；独立完成整进程隔离调查。对应 S08、P01–P07 适用项及 P05/Q3。

**Acceptance Scenarios**:

1. **Given** 工作区根内操作已授权，**When** 用户编辑文件并执行相关构建测试，**Then** 正常操作能够完成，不因名称为 write 或 bash 一律要求人工。
2. **Given** 操作命中硬 deny、角色上限或工作区外保护资源，**When** 受管工具尝试直接访问或经脚本、符号链接越界，**Then** 实际执行被阻断，即使模型返回批准也不能放行。
3. **Given** 选定隔离能力缺失或不可用，**When** 请求受保护操作，**Then** 操作明确失败且不回退宿主，诊断分别显示 profile、审批模式、隔离状态与未覆盖入口。
4. **Given** 整进程隔离尚未被声明支持，**When** 完成独立可行性与真实行为调查，**Then** 给出可核验支持路径或有证据的不支持原因；若声明支持，须另通过整进程负向验收。

### User Story 3 - 可选模型风险审批（US3） (Priority: P2)

Full 用户希望在明确授权范围内按需使用模型辅助风险判断，减少无谓询问；关闭时不产生额外模型消费，故障和拒绝不造成越权。

**Why this priority**: 审批是 Full 必须交付和验证的可选运行能力，依赖 US2 的权限边界；默认关闭不降低真实质量门槛。

**Independent Test**: 分别验证开启和关闭态的请求计数、拒绝、超时、取消、无界面处理与许可失效；使用冻结开发样本和独立保留集开展真实模型评测。对应 P08–P10，模型质量不能以机械安全测试替代。

**Acceptance Scenarios**:

1. **Given** Base 默认状态或 Full 关闭模型审查，**When** 用户执行日常任务，**Then** 额外审批模型调用为零；Full 普通操作也不逐次触发模型审查。
2. **Given** Full 启用已获准审批路线，**When** 审查返回 allow、ask、deny 或发生超时、协议故障，**Then** 结果与调用量可核对；ask 等待人工或阻塞，无界面也不自动放行，无隐式重试或切换 Provider。
3. **Given** 未执行许可已产生，**When** 用户取消、收紧限制或改变操作参数、目标、策略和执行上下文，**Then** 原许可失效且零执行；有效拒绝不能经等价改写或换模型反复争取。
4. **Given** 质量样本、指标和预算已在候选结果前冻结，**When** 完成真实模型评测，**Then** 分别报告六项质量指标与规则阻断结果；缺授权、未测或质量不达标时 Full 总交付不得通过。

### User Story 4 - 统一、有限委派（US4） (Priority: P2)

用户希望从 Pi 或 Codex 发起有限协作，选择首批 Pi/Codex 后端，并能看清实际执行模型、引导和继续同一任务。

**Why this priority**: 委派为复杂任务提供独立工作能力，也为 Task Keeper 提供一致的执行基础。

**Independent Test**: 从 Pi 与 Codex 使用 model-delegate，对 Pi/Codex 后端分别提交、观察、发送消息、继续和取消任务，并让两个受管进程竞争同一工作区。对应 F01–F04、F08–F10 与 X01、X02、X07。

**Acceptance Scenarios**:

1. **Given** Full 只运行主 Agent，**When** 用户提出普通小任务，**Then** 直接完成，不自动创建 Worker 或持久任务。
2. **Given** 用户按需发起 scout/worker/reviewer 协作，**When** 从 Pi 或 Codex 选择受支持后端，**Then** 使用同一 model-delegate 能力，显示父宿主、实际执行者、模型、上下文、状态和结果；不支持路线明确拒绝。
3. **Given** Worker 正在处理任务，**When** 用户查看进度、发消息、继续或取消，**Then** 可核对同一任务身份与状态；收到取消请求不等于工作已经停止。
4. **Given** 多个 profile 或受管进程访问同一工作区，**When** 同时请求写任务或某个 Writer 状态未知，**Then** 受管 Writer 总数不超过一个，未知 Writer 不释放保护、不创建第二份。

### User Story 5 - Task Keeper 工程流程（US5） (Priority: P2)

用户希望复杂 Inspect/Fix 任务经过计划、唯一写入者、可信测试与必要独立审查，失败时有有限返工和明确的未完成结果。

**Why this priority**: 工程任务需要真实测试与可追溯接受结果，不能仅依赖 Worker 自报完成。

**Independent Test**: 对合成 C++ 任务完成 Inspect/Fix，注入失败测试、零测试、旧证据、检查器篡改与超出两轮返工情况。对应 F05–F09、X02–X04、X07。

**Acceptance Scenarios**:

1. **Given** 用户提交已获准范围和预算内的复杂任务，**When** Task Keeper 执行 Inspect/Fix，**Then** 使用同一委派能力，提供计划、唯一 Writer、可信验证、必要独立 Reviewer 与最终验收，模型自报授权不生效。
2. **Given** 检查进程结束，**When** 出现非零、零测试、全跳过、输出缺失或失败断言，**Then** 测试不被接受，真实失败保留为失败证据；进程退出与最终接受分别显示。
3. **Given** 验收证据已经生成，**When** 相关未跟踪输入、配置、策略或检查条件改变，**Then** 旧证据失效，Worker 无法通过修改自己的可写配置降低通过门槛。
4. **Given** 检查或审查要求修复，**When** 已完成最多两轮定向返工仍未通过，**Then** 保留未完成状态，由主代理重新决策，不自动扩展为无限流程。

### User Story 6 - 持久只读任务（US6） (Priority: P2)

用户希望 Full 中的受限只读任务在前端退出后继续运行，重连或服务重启后仍能查找原任务，正确取消并获取结果。

**Why this priority**: 跨前端的任务连续性是 Full 必需能力；需独立于短命令和 Task Keeper 验证。

**Independent Test**: 从实际产品入口提交只读任务，退出前端、重连、受控重启、强制退出、取消并获取结果，注入响应丢失和身份不确定情况。对应 F11–F16、X01、X05–X08。

**Acceptance Scenarios**:

1. **Given** Full 已提交持久只读任务，**When** 用户退出前端并重新连接，**Then** 原任务继续且可通过稳定请求/任务 ID 查询、发消息或继续、取消和取结果，不重复提交。
2. **Given** 服务重启、响应丢失或进程身份无法确认，**When** 进行恢复核对，**Then** 保持同一任务身份；不能确认时显示 unknown/blocked，不自动重发可能有副作用或收费的调用，不创建第二份 Writer。
3. **Given** 任务具备受限只读能力，**When** 尝试写业务工作区或执行任意 Shell，**Then** 被服务端拒绝；仅允许在专用任务目录保存产物，前端退出不扩大授权。
4. **Given** 高级服务不可用或任务预算已经使用，**When** 用户继续普通编辑或恢复持久任务，**Then** 普通编辑仍可用，高级路径明确不可用或阻塞，重启不清零累计预算，未知额度不视为零或无限。

### User Story 7 - 长期维护与完整交付（US7） (Priority: P1)

用户希望两个 profile 可复刻安装、升级、诊断和恢复，账号、会话与活动任务受保护，并通过真实证据判断是否完整交付。

**Why this priority**: 安装与恢复贯穿所有阶段，故优先建立保护边界；最终维护、性能和总交付仍按既有依赖顺序随功能完成后验收。

**Independent Test**: 在隔离候选实例中重复部署并注入半途失败，分别验证配置、运行包及持久数据回退和等价插件替换；核对中文手册、四态性能对照和所有必需 gate。对应 M01–M07、F17/F18、S14 与最终独立审查。

**Acceptance Scenarios**:

1. **Given** 已有用户修改、账号、会话或活动实例，**When** 安装、重复部署、升级或失败恢复，**Then** 不覆盖其状态或所有权，不自动终止活动实例，仍有恢复引用的旧运行包保留。
2. **Given** 持久数据需要迁移，**When** 用户执行备份与恢复验证，**Then** 先从副本验证恢复，配置回滚、运行包回退和数据迁移分别报告，不承诺旧版本可读取新版本数据。
3. **Given** 某项能力需要更换插件提供者且存在可比较的行为约定，**When** 演练等价提供者替换及替换失败恢复，**Then** 配置入口、权限、账号、会话、未完成任务和既有证据受保护，兼容条件、状态归属、迁移、卸载与回退可核对；不兼容明确失败，不自动更换来源。
4. **Given** Base 已通过但 Full 或必需真实质量项未通过，**When** 评估交付状态，**Then** 按 Base 自身及共同能力的适用项独立报告 Base 通过并继续 Full；Full 专属功能、数据恢复和性能对照未完成不否定 Base 的有效证据。只有全部必需当前有效证据和无严重未关闭审查发现才判定总交付。

### Edge Cases

- 全局、项目、祖先目录或包资源隐式注入 Full 能力时，Base 独立性检查失败，不能仅依据 profile 文件声称独立（R02）。
- 凭据缺失、空值、不可读取或账号路线未获准时，明确诊断相应阻塞；不复制 token、不自动跨账号/Provider，不用模拟结果冒充真实认证（R03、R04、R09）。
- 隔离后端缺失、符号链接越界、项目脚本间接访问、网络或 Unix socket 越界时，实际阻断受保护入口；未覆盖入口如实显示（R12–R15）。
- 审批迟到、重复消费、动态脚本或依赖变化时，旧许可不能执行或缓存复用；无界面 ask、有效拒绝和模型故障分别报告（R16–R19）。
- 运行中取消仅确认收到请求但后代未停止时，不报告已停止，也不宣称简单改配置能立即撤销已获准的进程内操作（R06、R16、R27）。
- 启动后记录未保存、响应丢失、强制退出、PID 重用或双服务争用时，先核对真实状态；未知 Writer 不释放，未知调用不自动重派（R20、R26、R27）。
- 用户编辑器或未受管进程改变工作区时，不承诺阻止外部编辑，但相关输入与证据失效并触发冲突处理（R20、R24）。
- 零测试、全跳过、输出缺失或过期证据不能被接受；真实失败是有效失败证据，不用“记录无效”隐藏失败（R24）。
- 服务故障、存储只读、磁盘满、备份恢复或迁移失败时，不生成第二存储所有者，不清零累计限制，不自动结束活动任务换版本（R26–R32）。
- 无测量设备、缺真实账号授权、平台不支持或证据过期时，保留未测/阻塞/不支持/过期状态；只阻塞依赖路径，不删除必需目标或推定通过（R33–R36）。

## Requirements *(mandatory)*

### Functional Requirements

保留 R01–R37 作为稳定需求编号，其中 R01–R36 保留原编号和语义，R37 记录本轮新增的插件可替换要求；每条均由 [验收矩阵](acceptance.md) 映射到至少一个检查。以下是用户可观察能力与交付约束，内部设计见关联计划和契约。

- R01：使用未修改的正式上游运行包，只用公开配置、扩展 API、官方 CLI 与仓库适配；来源、完整依赖、宿主兼容性与运行时要求、许可证及安装脚本可核对。
- R02：组合共享配置与 Full 差异，沿用现有按 profile 分离的依赖及三方部署保护；Base 不安装、导入、注册 subagent、model-delegate、Task Keeper、Durable 及专用 Skill。逐项核对依赖声明与锁定结果、资源清单、实际安装内容及实际入口，不得通过全局、项目、祖先或包资源隐式注入。
- R03：两者有真实 Rotom 启动入口、独立可写状态与诊断。保持账号所有权和原生 home 身份，不复制 OAuth token、不制作刷新网关、不迁移活动会话。
- R04：原生模型登录与手动切换、受支持的私密文件 API key、账号权限、工具调用、重启与会话恢复分别验证。Base 验 Pi 主会话认证；Full 另验官方 Codex CLI 委派认证，不能因此使 Base 依赖 Codex 安装/登录。其他被选 provider 单列；主会话模型与委派执行器不可混称。
- R05：限定范围搜索、读取、修改、diff、相关构建测试和长命令均能工作。无需登记每一种日常 Shell 组合；固定命令可作为重复检查入口，但不能成为唯一日常开发路径。
- R06：普通长命令有日志、退出码、超时、取消和实际停止状态；Base 不承诺跨宿主持续运行，不依赖高级服务。
- R07：原生会话、压缩、必要分支/交接、按需 MCP/Code Mode；只保留一个自动压缩所有者。恢复后保留用户限制、失败证据和未完成任务引用。
- R08：中文、CLI/SSH、深色低干扰界面；模型、上下文、权限、错误与活动可见。只加载短工程规则、项目规则和按需领域知识。共享数据库 Skill 保留锁/MVCC/生命周期/恢复/兼容/最小修改/验证知识，受管调用流程放 Full 专用 Skill；尊重项目选择的 OpenSpec/Spec Kit，不全局叠加整套流程。选择终端模式以实际体验为依据。
- R09：按实际可用的既有国内路线验证无需海外代理；不宣称离线、不自动跨账户/Provider。禁止隐式遥测、收费、全库索引和无请求的模型调用。

- R10：产品 profile、审批模式、执行隔离是三个独立维度。Base 默认无模型审查；Full 提供默认关闭、可选启用的审查且普通操作不逐次调用模型；启用态真实质量验证仍是必需交付。安全能力不能依赖 Task Keeper 或 Durable。
- R11：权限规则只有一个权威来源；硬 deny、必须人工项和角色能力上限不可由模型覆盖。已授权的正常编辑/测试不因操作名为 write 或 bash 就一律人工。
- R12：必须交付至少一种经过目标平台真实验证的受管工具执行隔离路径，覆盖选定的 Shell/子进程与文件入口，并公布 MCP、Code Mode、用户 `!`、扩展、Worker、服务的覆盖矩阵。未覆盖入口不能被标记为已隔离。
- R13：沙箱复用 OS 原语或维护中的独立后端，不自建内核安全机制。具体后端在有界验证后固定；同一次验收周期不追逐每次上游发布。隔离不可用时受保护操作失败，不能偷偷退回宿主。
- R14：受管工具模式信任已锁定 Pi/扩展与宿主控制面，防范模型误操作和恶意项目脚本；不承诺抵抗同 UID 的主动本机对手或恶意宿主扩展。整进程隔离必须做独立可行性与行为验证，最终明确支持路径或有证据的不支持原因，不能长期只写“以后研究”。若将其选为支持能力，真实整进程负向验收必需。
- R15：保护运行包、策略、审批记录、认证及工作区外资源；明确读/写根、临时目录、网络、Unix socket、环境变量、缓存与子进程范围。网络白名单不等于内容防泄漏，工作区可写不等于源码不会误删。
- R16：审批输入绑定真实用户意图来源、最终操作参数、工作目录、会话、策略和执行上下文；一次许可一次消费。取消、限制收紧、参数/目标/策略变化使未执行许可失效。进程内已获准操作不会因简单修改配置而被宣称立即撤销。
- R17：单次模型审查使用显式获准路线、固定格式的 allow/ask/deny（允许/询问/拒绝）结果、请求时限和计量；无隐式工具、重试或换 Provider。此限制不禁止受预算约束的既定 TK 修复轮次、只读状态轮询和恢复对账。故障与有效拒绝分开处理；无 UI 的 ask 等待或阻塞，不自动放行。拒绝不能通过等价改写或换模型反复争取。
- R18：缓存只复用策略允许的确定性结论，不按命令前缀永久复用模型批准；动态脚本和依赖的变化不能靠命令文本摘要证明安全。审查结果不能成为提升 OS 权限的任意通行证。
- R19：审批质量按冻结样本与保留测试集分别评测误放行、误询问、协议失败、覆盖率、成本和延迟；规则阻断不能冒充模型正确判断，有限样本零误放行不等于普遍安全。

- R20：Full 默认单主 Agent；按需 scout/worker/reviewer，有限并发、明确实际模型、上下文、状态、消息、继续、取消和结果。多个 profile/进程访问同一工作区也只能有一个受管 Writer。
- R21：model-delegate 是共享 Skill 与统一且实际可用的命令行委派能力，首批 Pi/Codex 后端；Pi/Codex 共用同一委派核心，明确父宿主、实际 executor 与模型。使用公开协议，不解析 TUI、不调用私有宿主接口。
- R22：Task Keeper 共用同一委派核心，带可信任务/步骤/执行范围与预算身份。身份来自可信授权管理方；模型自报已批准或提供某个任务 ID 不构成授权。
- R23：固定 Inspect/Fix；计划、唯一 Writer、可信验证、必要独立 Reviewer、最多两轮定向修复和最终验收。超过次数保留未完成状态，主代理重决策；小任务走直接路径。
- R24：可信验证器独立于 Worker 可修改的配置，区分进程结束、测试结果、输入身份、审查与接受。非零、零测试、全跳过、输出缺失、过期证据不能通过；未跟踪输入及相关配置变化使证据失效。
- R25：Durable 是 Full 必需的独立持久只读任务路径。稳定 request/task ID、查询、消息/继续、取消、结果与重连；只读指执行能力受限，允许在专用任务目录保存产物，不包含任意 Shell 或业务写入。
- R26：一个持久服务拥有同一存储；Task Keeper 拥有阶段/验收，delegate 拥有后端执行，Durable 拥有持久任务恢复。不得为同一任务建多份权威队列或由多方自动重启。
- R27：启动成功但执行身份记录未保存、响应丢失、强制退出、PID 重用等必须对账；无法确认时 unknown/blocked，不重启第二份 Writer。不承诺外部副作用严格仅发生一次；读取重放也需核对输入身份、成本和策略。
- R28：持久服务按任务启动/连接，普通编辑不依赖其健康。凭据、权限和取消在服务端执行；前端退出不意味着后台获得新的授权，也不意味着收到取消。
- R29：用量视图区分已知、估计、未知和预留；预算约束仅覆盖实际可观测/可控调用。额度未知不是零或无限；重启不能清零任务累计限制，禁止未计量嵌套 Writer。
- R30：计划/diff 审阅、必要问题确认、长任务状态、日志、产物和错误恢复在终端可完成，浏览器增强按需。

- R31：候选运行包在隔离实例验证，安装/部署幂等、失败不破坏旧实例；保护漂移、账号、会话、活动进程及所有权。旧环境只做一次性回退，不维护第三条长期 legacy 产品线；有活动实例或恢复引用的旧包必须保留，不能以清理 legacy 为由终止或覆盖。
- R32：配置回滚、运行包选择回退和持久数据迁移分别处理。数据先做副本备份恢复验证；不承诺新版本数据库能被旧版本读取，不自动终止活动任务换版本。
- R33：性能对照纯 Pi、Base、Full idle、Full active；记录启动、首次就绪、终端交互体验、内存与处理器占用、上下文/工具元数据、调用量及释放。无测量设备的终端体验项保留人工验收；预算在测量候选结果之前冻结。
- R34：来源、命令入口、认证、权限、失败恢复、更新回退有短中文手册及可运行诊断。输出不含秘密、原始内部日志或认证摘要。
- R35：完成 Base gate、Full gate、隔离 gate、维护 gate 和已冻结必需平台/账号/体验项后才是总交付。未测、unsupported、needs-login、stale 不可抵作必需项通过；不因环境缺失自动删目标。 Base 可独立验收和发布，其门槛只计算 Base 自身及共同能力适用项，包括性能、安装恢复和提供者替换；不等待 Full 专属功能或四态完整对照。Full 与总交付仍要求全部相关项完成，按 profile 分列证据不能删减总目标。
- R36：持续执行维护 plan.md、tasks.md 和验收事实；每阶段通过继续下一阶段。只有用户停止、确实无可执行独立路径的阻塞、运行环境/额度限制或全部完成才结束实施。真实未知副作用先对账。

- R37：以用户能力与稳定行为约定为边界，具体插件提供者可替换；替换不得静默破坏配置入口、权限边界、账号与会话、未完成任务及既有证据。兼容条件、状态归属、迁移、卸载与回退必须可核对；不兼容明确失败，不自动把弃维护包换成未经选择的新来源。不要求建设通用插件框架。

### Key Entities *(include if feature involves data)*

- **产品 Profile**：`pi-base` 与 `pi-full` 的能力组合；共享日常基础，但具有独立可写状态、资源和可查询来源，Full 专属能力不进入 Base。
- **用户授权与权限策略**：真实用户意图、允许范围、硬拒绝、必须人工项和角色上限；是审批、执行与持久任务共同遵守的边界。
- **一次执行许可**：对特定最终操作及其工作目录、会话、策略和执行上下文的单次授权；变化或取消后未执行许可失效。
- **委派及持久任务**：稳定请求/任务身份、实际执行者、模型、状态、消息、产物、取消和预算记录；重连及恢复需能核对同一任务。
- **工作区与 Writer**：任务作用的工作区及唯一受管写入者；跨 profile 和受管进程仍共享“最多一个 Writer”的约束。
- **验证证据**：与具体输入、配置、运行版本和可信检查条件关联的执行、测试、审查及接受事实；失败、未测、过期与通过不能混用。
- **用量与预算**：已知、估计、未知及预留用量，与任务累计限制相连；未知不是零或无限，恢复不能重置累计使用。
- **受管交付与恢复资产**：正式来源、依赖锁定结果、用户修改、账号、会话、活动实例、备份与恢复引用；安装升级必须保留各自所有权。

## Success Criteria *(mandatory)*

### Measurable Outcomes

这些是待执行的交付门槛，不是已取得成绩；性能和质量的具体预算依赖基线与冻结程序，缺预算或缺真实证据不能通过。

- **SC-001 日常独立性**：Base 在 Full 专属依赖、服务和缓存均移除的情况下，完成 C++ 复现→最小修复→相关测试→diff 以及 Shell/Neovim 场景；无 Full 探测、隐藏 Worker 或额外审批模型调用（US1，R02–R09）。
- **SC-002 权限有效性**：所有硬 deny、失效或重复消费许可场景的执行次数为 0；至少一条当前 Linux 的受管工具隔离路径同时通过允许操作与越界负向检查；后端不可用时宿主回退次数为 0，覆盖矩阵和 Q3 整进程调查结论完整（US2，R11–R18）。
- **SC-003 审批开关与质量**：Base 默认和 Full 关闭态额外审批模型调用为 0；启用态在冻结开发集与独立保留集分别报告误放行、误询问、协议失败、覆盖率、成本、延迟六指标，达到候选结果前冻结的各项预算。六指标或预算缺失、真实质量未测不能通过 Full；规则阻断与模型正确判断分列（US3，R10、R17、R19）。
- **SC-004 有限协作与可信接受**：同一工作区的受管 Writer 数始终不超过 1；Task Keeper 定向返工不超过 2 轮。非零、零测试、全跳过、缺输出及过期证据的接受次数为 0；主宿主、实际执行者与模型可核对，终端能完成计划/diff 审阅、必要问答和状态查询（US4、US5，R20–R24、R30）。
- **SC-005 持久连续性**：退出前端、重连、重启和响应丢失后恢复同一请求/任务 ID；同 ID 不同请求明确冲突。未知状态自动重派次数为 0，未知 Writer 不释放，取消确认不冒充停止；业务写入和任意 Shell 执行次数为 0，任务累计预算不因恢复清零（US6，R25–R29）。
- **SC-006 安装升级保护**：冷安装、重复部署、半途失败、回退与数据恢复场景中，覆盖账号、用户修改、会话或所有权及自动终止活动实例的次数为 0；活动实例或恢复引用所需旧包保留，数据先验证副本恢复（US7，R31、R32）。
- **SC-007 性能与日常体验**：Base 独立验收要求纯 Pi 与 Base 的当前对照记录；Full 与总交付要求纯 Pi、Base、Full idle、Full active 四态完整记录；启动、首次就绪、终端体验、内存/处理器占用、上下文/工具元数据、调用及释放均满足候选结果前冻结的预算。Full idle 的额外模型消费与未经请求 Worker/Durable 数为 0；无可靠设备的体验项保留人工验收，缺基线、缺预算、未测不能算通过（US7，R33）。同机同方法且运行/输入身份仍有效的基线可复用，身份变化则重测；不能把 Base 两态通过算作 Full 四态通过。
- **SC-008 总交付证据完整性**：[验收矩阵](acceptance.md) 的 63 项检查（原 46 项及新增 17 项）中所有适用必需项均有当前有效的通过证据，8 项跨领域不变量均能逐项定位完整证据，R01–R37 均有追溯。Base、Full 按各自适用范围分别判定，最终要求两者、隔离、维护及冻结的当前 Linux、账号、体验 gate 全部通过，严重未关闭审查发现数为 0；未测、unsupported、needs-login、stale 不计通过。可选平台与可选 Stop hook 不适用项如实列出，不伪造通过（US1–US7，R35、R36）。
- **SC-009 可维护使用**：中文手册中的来源、启动、认证、权限、委派、停止、错误恢复及更新回退路径逐条核验可用；诊断和受控报告中秘密正文、秘密散列及认证摘要出现次数为 0。通过 Base 后继续 Full，阶段状态及验收事实持续一致（US7，R34–R36）。

- **SC-010 插件替换与恢复**：至少完成 1 组等价提供者替换与替换失败恢复演练，核对配置入口、权限、账号、会话、未完成任务和既有证据无静默破坏；兼容条件、状态归属、迁移、卸载及回退均可核对。不兼容情况明确失败，未经选择的新来源自动替换次数为 0。机制演练可用替代实现替身；真实产品支持仍须以实际组合验收，替身通过不能代替真实支持证据（US7，R37，M07）。

## Assumptions

- 本次唯一必需平台为当前 Linux x86_64；准备阶段核实内核、运行时、隔离能力及 profile/账号组合。macOS、Linux arm64、WSL2 等按需可选、不阻塞总交付，未执行不记通过。
- 使用未修改的正式 Pi 与官方 Codex CLI，并只通过官方配置、公开扩展能力和仓库自有适配集成；禁止修改上游源码、vendor/缓存宿主、官方二进制，禁止补丁重编译、monkey patch 或私有接口。历史偏离只作迁移依据，不能继续构建发布；迁移保护账号、会话与活动实例。
- 受管工具隔离为必交付，信任锁定宿主及扩展，不承诺抵抗同 UID 主动本机对手或恶意宿主扩展。整进程 Q3 可行性与行为调查必做，最终支持能力按证据决定；有证据的不支持结论只能闭合调查，不能替代受管工具隔离通过。
- 模型审批为 Full 默认关闭、按需启用的必交付能力；必须同时验证关闭态零调用和开启态 P08–P10，默认关闭不能豁免真实模型质量。独立 Reviewer 的必要审查职责与可关闭的风险审批功能分别按任务要求判断。
- 自动审核必须保留发送前严格输入上限；计量资格未验证时保持关闭，不能以本地估算、输出 maxTokens 或响应 usage 代替输入上界证明。按 2026-10-06 用户决定继续完成其他接线，Full 的启用态资格与质量仍单列为待验证。
- 本轮为长期实施；计划本身不授予未有的真实宿主、账号/付费模型、外部源码传输、发布或默认入口切换权限。执行沿用会话已有授权，不重复索取；缺授权仅阻塞依赖步骤，保留相关必需验收并继续独立工作。
- 默认测试只在仓库与临时 HOME/XDG 中运行，阻断网络、使用假子进程和虚构模型，不启动第三方宿主或读取真实凭据。真实 OS、原生宿主、账号模型和人工终端证据分层，不互相替代。
- 插件升级/替换的方向已明确，具体清单与版本、正式发行物兼容性、隔离后端与整进程调查、Pi/Codex 公开委派能力、持久服务生命周期均需准备阶段真实验证；现有依赖锁仅是调查基线，不能当作未来目标版本已确定；公开能力不足时如实记录限制，不以改宿主或假结果填补。
- 性能四态预算、模型质量六指标阈值、样本身份与测量方法需在查看候选结果前冻结；基线和评测尚未运行。这是明确的后续实证依赖，不是待用户选择的功能范围，也不是已有通过证据。
- 插件市场可能变化，长期维护以稳定用户能力和行为约定为边界，而非固定某个插件永不替换；不要求通用插件框架。不建设通用配置 DSL、任意 DAG、多层主管、全账户精确预算平台、自动合并、公网远程控制、自动全仓索引或新认证代理。Cursor/OMP 后端、DAP/LSP、高级上下文插件仅为可选候选，纳入必需范围须先明确；Stop hook 可选，缺失不阻塞产品。不修改 Codex 全局模型、审批、版本、登录或信任数据库。
- [计划](plan.md)、[任务](tasks.md)、[验收矩阵](acceptance.md) 分别保存实施安排、进度与事实；每阶段通过后继续，仅用户停止、无独立可执行路径的真实阻塞、环境/额度限制或全部完成可结束实施。替换全局默认、发布、推送或合并仍按各自授权。
