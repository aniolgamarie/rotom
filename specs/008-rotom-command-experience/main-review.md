## 3. OMP：升级没有解决共享资源归属

主线的实例、状态和缓存分别从 `instances_root`、`state_root`、`cache_root` 派生。
两个配置可以使用同一 profile/cache，分别使用不同 instance/state；OMP 包路径仍落到同一缓存 runtime。
所以 A 的 `unknown` 可以保存在 A 的 state root，而 B 的 Registry 为空；B 拿到包 EX 不能证明 A 已完整退出。
这是一种合法配置反例，不需要恶意编辑或绕过物理锁。

已合入主线的 `18.12.6` 升级没有修改 runtime/lifecycle/owner 协调路径。它的包组装与 Linux glibc x64
version/help、裸 RPC 配置加载、权限扩展注册/初始 sidecar 记录，不能证明跨实例 unknown、停止或恢复。

修订后的边界：

- T044 只收口通用 v2 观察、DSH/Pi 基础登记和 OMP 未登记兼容行为；不以 OMP 自动控制启用作为其完成条件。
- T045 与 US5 可在 T044 基础收口后独立推进。OMP 缺记录或物理占用仍显示未知/未登记，不能报告零实例或可维护。
- T065 定义规范物理 ResourceKey、唯一可信协调域锚点和完整 owner/reservation 引用；路径字符串或本实例空 Registry 不能证明完整覆盖。
- T066 在上述条件及相关测试成立后才接入 OMP v2 合作登记，并覆盖普通 sync 的修复/激活门禁；保留 cache-only sync 不创建实例的契约。
- 不同 state root 指向同一物理包时，只有能证明属于同一协调域且引用完整才允许自动维护；否则拒绝该自动能力。
  不为此扫描所有机器配置、认证目录、session 正文或系统全部 argv。
- 旧/外部入口仍依赖原物理租约；新协调协议不声称能让旧代码遵守其意图，也不能把包 EX、超时或 PID 消失当完整退出。

这样消除原先“T044 等 OMP 协调，T065 又间接等 T044”的依赖循环；没有删去共享资源门禁，
而是将 OMP 控制启用保留在真正建立资源协调之后。T044 仍未勾选，须按修订后的范围正式收口。
