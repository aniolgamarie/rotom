## 2. 已确定的产品方向

| 关注点 | 决策 |
| --- | --- |
| 命名与短启动 | 新增 `rotom`；日常使用 `rotom run dsh\|pi\|omp`，管理能力放在 `agent`、`term`、`work`，入口偏好放在 `config` |
| 旧命令 | 保留 `agentcfg`、`termcfg`、`work` 的参数、默认值、输出和运行路径；新门面调用现有业务模块 |
| 缺参交互 | `rotom` 提供任务导航；`rotom run` 等命令在满足 TTY 条件时提供合法选择。无 fzf 时可用编号；取消不默选 |
| 脚本使用 | `--no-input` 覆盖每个输入位置；缺必要参数或批准路径时明确退出，完整命令直接分发；操作原有批准仍然有效 |
| 可发现性 | 各级 help、菜单和 zsh 补全共享命令元数据；原生参数边界保持不透明，帮助不触发配置初始化或业务写入 |
| zsh 安装 | 由 termcfg 管理静态启动器、checkout 绑定和补全文件；第一次部署预览来源，已有绑定仅在显式选择时切换 |
| 日常恢复 | `rotom resume` 是独立任务；先交付 DSH 的确切 session ID、选择和实际恢复，再分别推进 Pi/OMP |
| 活跃实例 | 展示可证明的 PID、cwd、session ID 和终端位置；分别说明进程状态、会话可信度与恢复位置能力，未知字段保留未知 |
| 停止与维护 | 精确选择受管 run，保存最小恢复清单，优雅停止并证明资源释放；普通停止和维护共用执行路径 |
| 原 pane 恢复 | 优先验证现有 agentcfg 管理层的可选驻留模式，同时核实 Herdr 公开重启能力；先做能力原型再承诺位置保留 |
| 继续任务 | 恢复会话默认等待输入。“恢复并继续”单独选择，只有公开接口能证明接收目标与结果时开放 |

所有集成继续使用官方宿主、公开配置/插件 API 与 CLI，不修改上游源码。会话恢复表示重新加载会话；已中断命令的执行现场和外部副作用不属于恢复承诺。

## 3. 预期的日常路径

以下展示目标体验，详细参数位置见 [命令结构](design.md#3-命令结构与兼容策略)：

```text
rotom                                  选择启动、恢复或管理任务
rotom run                              选择工具和必要的目标
rotom run pi --profile pi-pro           直接启动已部署配方
rotom resume                           在确定范围内选择原生会话
rotom resume dsh --session SESSION_ID   恢复确切会话，默认等待用户输入
rotom agent --machine workstation instances list --agent dsh
                                       查看受管运行与可恢复性
rotom agent --machine workstation --profile dsh-default maintenance
                                       选择并审阅维护步骤
rotom term --help                      查询终端管理子命令
```

裸 session ID 只在已确定的 machine/local 范围内解析，不能跨原生 HOME 猜测归属。`--here` 选择终端位置，启动 cwd 仍按原会话规则核验；有活跃 writer、归属不明或能力不足时不以新会话替代恢复。

首次安装从 checkout 中的 `./rotom` 或兼容入口自举，预览并部署 zsh 入口后再使用 PATH 中的 `rotom`。需要分别初始化的 agent/term/work 配置仍各自明确处理，详见 [首次使用路径](design.md#74-首次安装与日常入口衔接)。

## 4. 交付顺序与完成标准

| 阶段 | 交付结果 | 必须满足的门槛 | 对应需求/能力包 |
| --- | --- | --- | --- |
| 一：统一入口 | 三工具短启动、偏好、各级交互/help/补全、zsh 受管入口 | 新旧命令兼容、no-input 和原生尾部正确；生成绑定的计划、journal、中断恢复和回滚通过隔离验证 | R1–R6；设计 A–F |
| 二：DSH 日常恢复 | 已确认的 session ID 展示/查询、范围内选择、当前终端实际 resume | 当前官方通道可用，原生 HOME/cwd/会话身份正确，writer 排他与加载结果可证明 | DSH 的 R8；最小 M1 + M3 |
| 三：停止与维护 | 实例页、精确停止、保存清单、执行已选维护、恢复或保留待恢复结果 | 对应工具已有恢复证据；退出/资源释放、准入意图、部分失败、取消和 no-input 有界返回均可验证 | R7 的停止/维护；M2 |
| 四：原位置恢复 | 支持的原 pane 等待和重新启动，或已验证的公开重启 | 明确首次采用方式、新 run 身份、租约释放、PTY/信号、控制请求代际与管理代码兼容 | R7 的位置恢复；M4 |
| 独立扩展 | Pi/OMP 恢复、OMP 工作区 type、明确选择的继续 | 每个工具/能力分别取得证据；自动继续还需准确输入目标与接收确认 | 各工具 R8、M5 及独立工作区扩展 |

第一阶段可以注册 `resume` 的静态语法/help 并解释未准入能力；这个入口不计作实际恢复交付。第二阶段应尽早实现，不等全部维护功能或三个工具同时准备好。

原位置能力原型可与前面阶段并行。它未通过时，维护只能使用事先接受的新位置或人工恢复方式；没有对应恢复证据时，普通停止须明确说明需人工恢复。自动继续可保持未开放，不阻塞日常 resume。

### 阶段一的实施拆分

按 A 命令注册与 scope → B 偏好/短启动 → C 输入门控 → D help/补全 → E 受管入口 → F 文档收口推进。A–D 的业务分发与 E 的生成产物应分开验收；E 的事务、日志和恢复语义由主代理负责关键判断。

后续并行任务按文件所有权分配，避免同时修改同一处理器。普通 run、日常 resume、实例 stop 各保持一个共享执行契约；维护只编排这些能力，避免再建立一套会话数据库或执行平台。

## 5. 必须先验证的能力

| 能力问题 | 当前判断 | 通过后才开放 |
| --- | --- | --- |
| DSH `runProfile` 如何接入公开会话恢复与事件 | 上游启动器存在相关通道，当前托管路径仍需原型验证 | 确切 session ID 与实际 resume |
| 会话 writer 排他、cwd 和加载结果 | 不能以“有历史记录”或两次读取无 writer 代替证明 | 自动恢复与后续输入 |
| 停止后是否仍有子孙进程或持有资源 | 不能只看单个 PID 消失；旧登记缺字段时保留未知 | 维护准入与“可安全更新”提示 |
| agentcfg 驻留是否保留原 pane 并正确交接终端 | 现有 agentcfg 已是父进程，宿主退出后等待/恢复是新增模式 | 原 pane 恢复 |
| Herdr 锁定版本的公开 stop/respawn/input 能力 | 当前 Rotom 准入未提供，不据此推断上游不存在 | 对应终端控制动作 |
| 管理代码更新后的驻留兼容 | 首版发现管理源码/协议变化时拒绝旧进程原地恢复，转新位置；handoff 单独验证 | 更新管理代码后仍留在原 pane |
| OMP 受管恢复边界 | 现有入口拒绝可能改变 cwd 的恢复参数，暂不放宽 | OMP 自动恢复 |
| “继续”是否准确送达一次 | 没有幂等键/接收确认时，未知结果不能重发 | 恢复并继续 |

这些是实施证据门槛，当前没有环境验证通过的结论，也不要求为整理文档先运行真实宿主。默认测试使用临时 HOME、假进程和阻断网络；真实 Agent、Herdr、zsh、信号及 PTY 验收需另行明确授权。
