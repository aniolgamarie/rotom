# 活跃实例、维护停机与会话恢复设计

状态：新增需求的探索方案，尚未实现；公开接口、进程退出证明与原 pane 保留需先做独立能力验证。
关联：[当前计划总览](README.md)、[统一入口方案](design.md)、[审阅记录](review.md)。设计源码基线为 `17bbacd6ab8be8f397e6356ce21822b422b41eed`；后续 `main` 变化见 [基线复核](review.md#整理更新与基线复核)。

## 1. 用户要完成的任务

更新 DSH 配置前，用户需要知道哪些运行会阻止维护，停止它们并释放真实租约；更新后，尽量在原来的项目和终端位置恢复各自会话。一次维护不应要求用户逐个查 PID、记 session ID、关闭标签页，再手动重建工作现场。

建议提供一个可交互的维护操作页，串起“查看受影响运行 → 保存恢复清单 → 停止 → 执行已选维护 → 恢复会话”。普通停止也可以单独使用。

必须区分三个结果：

1. 进程已经退出、相关运行资源已释放，可以维护。
2. 新进程已经加载原来的原生会话，等待用户输入。
3. 已向确认身份的 Agent 发送新指令，开始继续任务。

恢复会话不承诺恢复已中断的外部命令、撤销工具副作用或从进程内存原点继续。第 3 项是单独的明确选项，默认恢复到可查看的会话，不自动发送“继续”。

## 2. 当前证据与能力限制

| 能力 | 当前已知事实 | 设计结论 |
| --- | --- | --- |
| DSH/OMP 活跃运行登记 | 当前使用共享 lifecycle lease，没有 Pi 式 run owner 登记 | 必须先补运行元数据；不能直接承诺已有完整实例列表 |
| Pi owner | 有 run ID、manager PID/birth identity、状态和资源；目前实际注册不含 cwd/当前 session ID | 复用退出证明，补字段不能把已有 unknown 变为 idle |
| 原 Herdr pane | `rotom-work-shell` exec 到 `agentcfg run`；agentcfg 已是父进程并同步等待官方宿主，宿主退出后它也返回退出 | 应优先扩展现有管理路径的可选驻留模式，不能把已存在的父进程管理层遗漏掉；原 pane 保留仍需验证 |
| 原生会话恢复 | DSH TUI 上游有明确 session 恢复通道；当前受管路径与其启动器不是同一条参数解析路径 | 需单独验证托管适配，不直接把 `--resume` 当作已可透传功能 |
| OMP 恢复 | 当前受管入口拒绝 resume/continue/session/fork 参数，原因是恢复可能改变 cwd | 不能为统一按钮放宽这条边界；先标记手动/不支持 |
| 业务输入 | 当前 Rotom 的 Herdr 方法准入没有 pane input/run、stop 或 respawn | 未准入不证明上游不存在；需按锁定版本审计公开能力，禁止盲目注入终端文本 |

## 3. 用户界面与命令建议

以下为拟议命令，不是当前可执行接口：

```sh
rotom agent --machine workstation instances list --agent dsh
rotom agent --machine workstation --profile dsh-default maintenance
```

`instances` 是实例操作页，`instances list` 是可直接调用的只读查询；`instances stop` 复用下文的停止计划和精确目标确认，可单独停止所选 run，不要求随后更新配置。非交互停止必须引用已审阅的计划，不能仅给模糊过滤条件就控制所有匹配进程。

实例查询列出所选 machine 内的受管运行；没有显式 profile 时不自动缩小为 `default_profile`，可按工具或 profile 过滤。它不靠扫描全部系统 argv、cwd 或会话正文发现“所有 DSH”。受管租约存在但没有可验证记录时，显示未登记活动/未知项，不把它当作零运行。

维护操作页示意：

```text
维护范围：workstation / dsh-default
操作：更新配置与锁定依赖（setup）

选择  运行    PID    项目目录             会话        终端位置       可恢复性
[x]   run-a   4101   /path/to/project-a   session-a   work-a/tab-2   同会话；原位置待验证
[x]   run-b   4108   /path/to/project-b   session-b   work-b/tab-1   同会话；新标签页
[ ]   run-c   4117   /path/to/project-c   未知        普通终端       需人工选择会话

动作：查看详情 / 保存清单并停止所选 / 查看待恢复批次 / 返回
```

PID 是当前观察值，不是供后续裸 `kill PID` 使用的唯一身份。详情分开展示 manager、宿主和已归属的辅助进程；session ID 与工具/profile/原生 HOME 共同标识会话，目录只是启动 cwd 或明确记录的会话 cwd，二者不同时分别显示。

列表分开展示“进程存活/已退出/未知”“会话 ID 已确认/历史记录/未知”“支持的恢复位置”。不能用一个绿色 ready 同时表示这三件事，也不从进程存活推断 Agent 正在执行任务。每项观察附来源与时间，缺少字段的 backend 按项降级。

非交互操作可拆为可审阅步骤：

```text
rotom agent ... maintenance plan --operation setup
rotom agent ... maintenance stop --operation setup --plan-id PLAN_ID
rotom agent ... maintenance execute --batch BATCH_ID
rotom agent ... maintenance restore --batch BATCH_ID
rotom agent ... maintenance status --batch BATCH_ID
rotom agent ... maintenance cancel --batch BATCH_ID
```

`plan` 只读。`stop` 接受已经审阅的精确目标集合并保存批次；`execute` 仅执行该批次声明的维护操作。TTY 操作页可以在一次明确审阅后顺序调用这些步骤，仍保留原操作的接管和配置检查；发现范围、来源或目标变化时重新审阅。退出页面不会自动停止、维护或恢复。

plan ID 是内容摘要，不是可以查询任意历史目标的数据库键。非交互 `stop` 必须重复计划的 machine/local、profile、operation 和显式选择的 `--run` 集合等输入，重新计算资源/身份快照后核对 ID；TTY 可以保留同一计划对象并在执行前复核。默认选全部相关运行也是计划的一部分，有新运行时旧 ID 失效。原例中的省略号表示同一明确作用域，下一步提示必须输出完整 token。

普通实例停止同样支持只读 `instances stop --run RUN_ID --dry-run`，真正停止时带回相同的 `--run` 集合和 `--plan-id`；不会只拿一个不可逆的摘要就猜目标。`--dry-run` 不建立批次、准入意图或控制请求。`stop` 接受并复核后才持久化批次。

`cancel` 表示不再继续这个批次，不撤销已完成的停止或配置变更。它必须先对账在途操作；结果未知时不能用取消来清理 owner 或掩盖未完成维护。需要恢复的已停止运行仍保留清单，用户可以之后单独处理。

### 3.1 非交互与部分结果

`instances` 和 `maintenance` 的结果使用 agent 命令的 `--format auto|human|json` 约定。输入门控与根命令一致，`--no-input` 不代表批准，JSON 不生成接管、强制或继续授权。

等待退出和后台恢复确认的控制命令提供 `--wait-seconds`，默认 30，允许 1–300。预算用尽后保存部分结果并返回，不自动重发信号、不自动强杀、不继续 execute/restore；这个预算不替代既有安装超时、work 单次 deadline，也不限制明确交接到当前终端的普通会话交互时长。TTY 可以在结果页明确开始下一次等待。

| 情况 | 结果与下一步 |
| --- | --- |
| 参数/批准缺失，或操作只有交互批准路径 | 退出 2；不读取 stdin，不执行缺少批准的动作 |
| 活动/未知运行未退出、控制结果未知、待恢复事务或计划漂移 | 退出 4；停止后续步骤，保存已停止与未决事实 |
| 已明确的依赖或公开能力不足 | 退出 5；不假装恢复成功 |
| 已执行的 setup/apply/sync/rollback 失败 | 保留原操作退出码、原因和已完成效果；不自动恢复宿主 |
| 需要新预览/接受 | 标记 review_required；给出带 batch 和原 scope 的计划命令，不自动接受新范围 |

每个最终结果至少含 batch ID（尚未创建时为空）、请求及实际影响范围、逐运行 stop/restore 状态、维护是否派发及其原结果、是否需重新审阅、一个主要 next_command 与必要的逐项提示。结构化结果只挑选已声明的非秘密字段，原操作进度放 stderr，不将 text setup 输出混入 JSON，也不采集会话正文。

`execute --batch` 是请求执行该批次记录的操作，不是万能授权。原接受快照仍匹配时才继续；变化时返回 4，使用只读 `maintenance plan --batch BATCH_ID` 重新预览，再由 `execute --batch BATCH_ID --plan-id NEW_PLAN_ID` 明确接受该版本，保留原操作的其它接管/确认要求。批次 ID 不能改变 operation、悄悄扩大运行集合或替代缺失批准。

## 4. 运行元数据与恢复清单

在新的受管启动路径中登记一条 run 记录，并通过公开生命周期事件维护它：

- 作用域：machine/local 的安全标识、工具、profile、实例和保存的部署/运行包身份。
- 进程：run ID、manager 和宿主的可验证出生身份、开始时间、归属的资源与观察覆盖范围。
- 位置：启动 cwd、明确报告的当前会话 cwd，以及 Herdr endpoint generation、workspace/tab/pane/terminal 身份和归属证明。
- 会话：当前 backend + native HOME + session ID、更新时间和来源；用户在 TUI 内切换/新建会话时需更新，不能只保存第一次启动值。
- 能力：能否请求停止、能否证明完全退出、能否按确切会话恢复、能否保留原位置、能否确认可输入状态。

未知字段显示未知；过期字段显示记录时间。session 目录不是活动 session ID，Herdr marker 也不是 Agent 仍存活的证明。父进程、会话和子任务可以是一对多关系，列表不能把多个原生会话压成一个“当前可恢复会话”而隐瞒其它活动。

停止前的记录不一定是退出时的最后会话。每个观察来源需绑定 emitter/run 代际和单调事件序号，每次批次清单更新保留版本。停止派发前重新核对 session 引用与代际；预览后切换会话时重新说明实际受影响目标。

停止期间若发生切换，只能根据可证明完整的最终事件边界更新并封存清单，再将该版本用于恢复。仅有时间戳、没有最终观察、事件有缺口、强杀前未落盘，或退出后不能证明实际 session 时，清除“确切会话可恢复”标记并要求人工选择。不得用最近一次看见的 ID 代替最终身份；公开接口没有封口能力时，该路径就不具备自动恢复资格。

停止前保存最小恢复清单：明确运行身份、会话引用、cwd、原位置、经过允许字段筛选的启动参数、停止前部署身份和预期维护结果。环境只保存继承/删除策略和必要名称；恢复时重新执行当前环境与凭据解析，不保存完整 environ、token、原始 argv、对话正文或工具输出。不承诺逐字复制旧进程环境；必要工具链缺失时标为需准备。

清单和操作日志存放在私人状态目录，目录/文件权限 `0700/0600`，有版本、完整性、原子更新和未知字段拒绝。它是可恢复操作记录，不是会话数据库备份。CLI 和结果摘要不输出私人原始日志或秘密。

旧 checkout 或非受管启动的活动不能自动纳入控制。允许展示确有来源的提示，但停止/恢复前必须具备明确归属或转为人工处理；不以进程名包含 dsh、相同 cwd、标题或相同用户作为控制权限。

## 5. 一键停止的语义

默认按钮是“停止所选并等待退出”，优先使用已验证的官方退出/取消接口；否则由相应适配器使用平台支持的稳定进程身份发送有界的温和信号。优雅退出的实际行为需要按工具和版本测试，不能将一次信号自动当作成功。

停止动作只针对计划中已核验的 Agent 运行及明确归属的子进程。不能按系统进程名批量 kill，不能杀 Herdr server、编辑器、其它 shell、其它用户作业，不能因 cwd 相同而扩大范围。确认后、发送前重新核对 PID 出生身份，防止 PID 复用；没有可靠平台能力时拒绝自动停止。

等待期间保留负责退出观察的 manager，不能先杀观察者再推断子进程全部结束。工具、MCP、Teams/子 Agent 和脱离的后台后代都必须按已有覆盖规则处理。Pi 继续要求完整后代退出证据；未知 owner、存活后代或未覆盖资源继续阻止维护。没有退出证明时不清 marker、不删锁、不以超时或用户确认替代内核/协议证据。

超时后列出未退出项和影响，提供“继续等待 / 取消后续维护 / 强制终止这些已核验目标”。强制终止是另一项明确动作，只影响重新核验的剩余目标，报告会话或工具输出可能尚未完整落盘；强杀后仍重新确认资源释放。未证明恢复所需会话信息的项在停止前醒目标记，默认不把它们描述成可恢复。

一次批量停止可以在审阅全部目标后统一确认，不要求用户逐个输入 PID；明确选择的批量动作也不代表其它未知活动被允许自动清理。

## 6. 维护期间的准入与持久状态

建议为受影响资源集合建立可恢复的维护意图，与现有 run admission 和 exclusive maintenance lease 协作：

1. 先根据当前变更和既有操作契约判断是否需要停机；没有所需变更且运行包无需修复时直接报告无需维护，不停止运行。需要维护时计算实际资源闭包，列出所有已知阻塞运行，不默认停止整台机器上的全部 DSH。
2. 用户接受后，在短准入临界区原子核对并登记规范化物理资源集合、批次 ID 和代际。首版明确拒绝与未完成或 unknown 批次重叠，不隐式排队或接管。阻止遵循该协议的新运行进入这些资源，再释放短锁等待已有运行退出。
3. 等待、用户确认和子进程/终端握手期间，不持有需要对方退出路径获取的登记锁或 work operation 锁。
4. 全部相关资源已确认空闲后，按现有锁顺序获取独占维护租约。维护来源/计划变化需重新预览，不能把停止前失效的部署计划直接用于写入。
5. 执行原有 setup/apply/sync/rollback；保留其独立 journal 和失败语义。维护失败时暂停后续步骤，展示原部署、部分完成和明确恢复选项，不自动重新启动可能不兼容的会话。
6. 恢复前释放独占维护租约；为每项恢复绑定精确的批次代际、后继 run/op 和预期部署版本，发放一次性准入许可。每次启动仍核对全部相关意图，不绕过其它批次；这不是资源或 profile 的一般白名单。批次结束或用户明确取消后，只能解除 ID 与当前代际匹配的本批意图；真实活动/未知 owner 或配置恢复阻塞保持不变。

维护意图是合作协议。旧 checkout 和外部非受管入口可能不识别它；现有物理租约仍是最终维护门禁。出现新活动时重新报告阻塞，不擅自杀掉它来完成批次，也不承诺已经阻止全系统启动。

批次至少区分：planned、stop_requested、stopped_confirmed、maintenance_dispatch_intent、maintenance_running、maintenance_failed/partial、restore_pending、launch_dispatched、restored、unknown。每个运行分别记录状态。实际维护调用前必须持久化 dispatch intent，任何崩溃窗口都不能把“可能已派发”误判为“从未派发”。unknown 意图不会因超时或另一批次到来被替换。

控制请求超时/回包丢失保持 unknown，通过只读事实对账；不能再次发送启动或继续指令来“试一下”。一次性恢复许可已可能消费但结果未知时，同样先对账，不重新签发一个许可重试。

取消或 manager 崩溃时保留已完成和未决事实，后续从 `maintenance status` 进入恢复；不自动重启，不回滚已经独立完成的工具副作用。

## 7. 在哪里恢复：推荐保留终端容器

恢复结果应写清楚三个身份：原原生会话、新 run/进程，以及终端位置。同一会话恢复后 PID 和 run ID 必然可以变化；保留原 pane 也不意味着旧进程被复活。

建议按能力提供以下选择，默认选择已验证且用户接受的方式：

| 方式 | 条件与效果 |
| --- | --- |
| 原位置恢复 | 原 pane 仍有已核验的受管等待入口，或上游提供并已验收可绑定身份的公开重启接口；重新加载确切会话 |
| 原工作区的新标签页恢复 | 旧位置无法安全复用但工作区身份可验证；明确告知新建 tab 和新 run，不覆盖原来的其它进程 |
| 当前终端恢复 / 复制恢复命令 | 普通 shell 或原 Herdr 位置已失效；用户选择在当前终端执行，或手动在目标终端执行 |
| 需人工处理 | session ID 未知、原生恢复不支持、旧启动仍可能存活、cwd/权限不兼容或状态未知 |

为了长期稳定保留原位置，优先在现有 `agentcfg`/`rotom` 启动管理层增加显式的可选驻留模式。当前普通路径已经是：

```text
Herdr pane → agentcfg run → 官方 Agent 子进程
                         等待退出 → 返回退出码 → agentcfg 退出
```

拟增加的模式在一次 `runtime.run` 完整结束后保留外层进程，显示“已停止，等待恢复”；收到经过核验的恢复请求后，为下一次运行重新加载目标和部署契约、解析当前环境/凭据、执行全部准入，再启动官方子进程。复用现有适配器和运行路径，不在外面再叠一套独立启动系统。正常单次 run 继续保留宿主退出即返回的 CLI/脚本行为；Herdr type 是否采用驻留由明确的启动契约选择。

首次采用时，已经运行的普通单次 manager 不会因为更新配置而变成驻留进程。预览须逐项说明“本次可保留原位置 / 本次只能新位置或手动 / 以后新建实例可采用驻留”。采用新 type 契约需经原有新实例/rebind 检查，不能在线改写活动实例。用户要求原位置而当前不具备能力时，在停止前允许保留运行或重新选择恢复位置，不能等停机后才披露。

驻留等待必须位于单次运行的租约/owner 生命周期之外。当前 `runtime.run` 在上下文中持有物理、状态和运行包租约；不能在这些上下文内部等恢复，否则更新仍会被它自己阻塞。先按原规则完成子孙退出观察和本次资源收尾，再进入 parked；`runtime.run` 返回本身不代替完整后代退出证明。空闲外层不持有 Agent 的 shared run lease，也不沿用旧 workspace 对象、运行包、凭据快照或已消费的启动许可。

恢复请求需要核验本 pane 的实例、代际和一次性操作 ID，只在确证 parked 状态执行。控制端点使用私人权限与明确调用者校验，不能从任意终端文本启动命令。该模式不运行模型、不做任务调度，不重新引入已退役的执行平台。

还须分清配置/Agent 运行包更新与 Rotom 管理代码更新。驻留进程记录管理源码及控制协议身份；重新读取 workspace 不会刷新已导入的 Python 模块。首版在继续处理恢复前核对管理源码/协议，若发生变化，拒绝在旧进程中直接恢复，给出从当前可信入口在新位置恢复的方式，并保留原 pane/清单等待人工处理。不能靠后续 import 或 `importlib.reload` 混合新旧管理代码。

同一管理代码身份下，配置及 Agent 运行包可按新部署契约重新校验使用。管理代码变更后的无缝原 pane 恢复留待可验证的无租约 re-exec/handoff，须另审控制端点、代际、一次性请求、FD、环境、信号和崩溃窗口。该限制不阻塞使用新终端的日常 resume。

这属于新能力，须先证明 PTY 前台进程组、Ctrl-C/退出、终端模式恢复、manager 崩溃、后代观察、旧 pane/endpoint generation 和重复请求的正确性。当前 `work` 把 terminal 身份与一次启动绑定，不能复用已消费的 accepted/op 冒充新启动。需要显式区分终端容器与每次运行的身份，并为 parked/restart 状态设计新版本契约。

如上游公开接口已能安全完成此任务，应优先比较其能力和限制；不能因为当前适配器 allowlist 中没有某方法，就断言 Herdr 不支持。不能使用轮询标题、猜测 shell 已闲置或发送一串按键代替受管等待入口。

## 8. 恢复哪个会话、采用哪套配置

默认恢复维护前记录的确切 session ID，不使用“最近会话”标记替代。恢复前确认旧会话没有其它活跃 writer，且原生会话存储和当前部署允许该 cwd/权限。恢复失败不得悄悄创建新会话并显示成功。

恢复的部署依据分三条路径：

| 批次事实 | 允许的恢复依据 |
| --- | --- |
| 仅停止，或可证明维护从未派发，当前部署仍匹配停止前快照 | 经用户审阅，使用停止前的已保存部署契约；仍重新检查运行包与依赖 |
| 维护成功，结果和部署身份已记录 | 使用本批成功后保存的部署契约 |
| 维护部分完成、已经可能派发或结果未知 | 先按原 journal 恢复/对账，形成可接受的新部署契约并重新审阅；不直接退回停止前契约 |

各路径均保留原 machine/profile/native HOME 和经核验的会话引用。当前部署与批次预期不同、会话迁移或格式不兼容时，重新预览或转人工，不自动降级运行包、改会话文件或回滚数据库。取消只取消剩余动作，已停止的运行保持待恢复及其清单，不标为已经恢复。

工作区已有固定 binding 不能被直接覆盖。新运行必须有新的 run/op/receipt；若维护更新改变了工作区固定启动契约，需通过明确的后继绑定/rebind 流程，并证明旧业务运行完全退出。现有仅凭 pane 存在判定 active 的实现不足以处理 parked 容器，必须在新生命周期契约中解决，不能直接放宽旧 rebind 检查。

DSH 首先验证公开 session 配置/事件通道如何接入当前 `runProfile` 路径，保持官方宿主和公开插件 API 不变。Pi 复用现有 owner 证明并单独验收官方恢复路径。OMP 在受管 cwd 恢复边界未有可验证设计前，明确不支持自动恢复。

维护中的恢复复用 [日常 `rotom resume` 接口](design.md#43-日常会话恢复入口) 的作用域解析、session 身份、writer 排他和结果确认；批次只补充受影响目标、预期部署和已接受的位置选择，不发明另一套会话选择与启动逻辑。

普通非 Herdr 终端没有可安全定位的远端输入目标。批量恢复不能向发起维护的同一个 TTY 同时启动多个交互 TUI；只能逐个进入、输出恢复命令，或经用户明确选择新建受支持终端位置。

## 9. “恢复并继续”作为额外选项

默认按钮“恢复会话”只加载历史并等待。另设“恢复并继续所选任务”，在批次审阅中展示目标会话及将发送的文本；可以一次确认多个明确目标。

发送前必须从公开协议或事件确认：接收端是本次新 run、原生 session ID 匹配、没有其它 writer、界面已进入可接收新用户消息的状态。登录页、权限问题、shell、崩溃页和仅有历史加载事件都不满足这个条件。没有可验证输入接口时只提供复制文本与聚焦，不自动键入。

恢复和发送之间的 writer 排他需要覆盖“检查后到执行”的竞争窗口，依赖原生 writer 租约或等价公开的原子能力。连续读取两次“没有其它 writer”不构成排他；缺少该能力时不开放自动恢复/发送路径。

建议继续文本包含“先检查中断前结果和当前工作区状态，再继续未完成任务，避免重复已经完成的操作”。它仍是新的用户指令，不是幂等保证；原生权限和审批不改变。

每次继续有独立 operation ID、目标、请求状态和可验证的接收结果。没有上游幂等键/确认能力时，超时后保持未知且不重发，交给用户检查。会话恢复成功、继续未发送或结果未知分别报告，不合并成“全部恢复完成”。

## 10. 能力包、依赖与验证门槛

M1–M5 是能力包编号，不是必须按数字执行的时间顺序：

| 能力包 | 目标 | 前置证据 |
| --- | --- | --- |
| M1 | 按 backend 逐步登记运行、只读实例页和可恢复性说明 | 首个 DSH 最小字段及来源，session 切换事件、未登记租约和非秘密读取边界；不要求三工具同时完成 |
| M2 | 保存清单、批量优雅停止及维护操作页 | M1、对应 M3 恢复证据、稳定进程身份、退出证明、非交互预算、准入和部分结果 |
| M3 | DSH 确切会话恢复，明确原位置/新标签页/手动选择 | 官方会话通道与当前适配、writer 排他、cwd、部署和会话格式验证 |
| M4 | 原 pane 保留与恢复 | M1/M3、新容器/run 身份模型或已核验公开 respawn，首次采用、管理代码兼容、PTY/信号/租约和重复请求验证 |
| M5 | 明确选择的批量继续 | 可证明的 session-ready/input 目标、批准范围、接收证据和未知结果处理 |

推荐路径是统一入口 → DSH 最小 M1 + 当前终端 M3 → M2 停止/维护 → 已通过验证的 M4 原位置恢复。M4 可提前独立做能力原型，但未完成时 M2 只使用预先接受的新位置或手动方案。M5 自动继续单独开放，不阻塞其它能力；Pi/OMP 分别按自己的证据推进。

新 UI/help 可以解释这些状态，但 M2–M5 不能因菜单已存在就变成可用功能。统一 CLI 第一阶段可独立交付，不用临时 `pkill` 或键盘注入填补接口缺口。

日常 resume 的接口和最小能力原型应尽早独立验证，不等批量维护全部实现后才处理。M2 若要向用户承诺“停止后可恢复”，必须先有对应工具的 M3 最小恢复证据；没有该证据时只能提供明确标记需人工恢复的停止操作。

默认测试使用虚构运行、临时 HOME、假进程/内核观察和假 endpoint，覆盖 PID 复用、会话切换、幸存子孙、外部新运行、锁顺序、manager 崩溃、原 pane 消失/复用、旧 endpoint、维护部分失败和重复恢复/输入。真实停止、信号、PTY、Herdr/Agent 启动和自动继续都是独立显式验收，本次没有执行。

额外必测：只读 plan 的输入重建与过期 ID、部分停止后的 no-input 有界返回、计划变化不自动接受、原操作失败的 JSON/退出码保留、旧单次 manager 首次采用驻留，以及管理源码变化时的拒绝/降级。这些默认检查仍使用假进程、假时间和文件哨兵。
